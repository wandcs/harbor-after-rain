# 开发约定

版本：1.2。日期：2026-11-15。适用于本仓库后续开发与维护。

本文确定工作规则和目标工程布局；目标目录、命令和服务能力在对应实施任务中交付。联网实现进度和实际验证状态见[分阶段实施计划](online-implementation-plan.md)。

产品行为见[联网产品设计](online-product-design.md)，网络机制与实验参数见[联网技术方案](online-technical-design.md)，发布操作见[发布与运行约定](release-runbook.md)。

## 1. 目标、决策与权限

优先追求用户目标和已确认原则，再依据可靠证据选择实现。计划、当前代码和测试都可修订；不能为保住实现或让测试通过，擅自改变产品约定。

| 情况 | 执行方式 |
| --- | --- |
| 已授权目标内的文件拆分、内部算法、可逆重构及工程细节 | 自主决定，记录重要理由，完成验证 |
| 已约定进入或停止条件得到证据支持 | 直接应用条件，说明结果，不要求用户重复确认 |
| 技术参数尚需实验收敛 | 记录初值、实验与调整依据，不写成产品保证 |
| 改变产品目标、明确的体验或验收条件、支持范围、信任或数据边界 | 暂停依赖该决定的工作，提出证据、替代方案和推荐；继续独立工作 |
| 新增明显的长期维护、部署或付费成本，且无既定授权覆盖 | 先说明收益、成本、替代方案和推荐，再决定是否引入 |
| 推送、公开发布、购买或其他外部操作 | 按任务已有授权执行；缺少授权时，先准备可审阅结果，再讨论该操作 |

授权跨轮延续，不能把本文当作重复索取确认的理由。制定规范不构成开始联网实现、购买服务器或公开发布的授权。

文档中的决定标注为“已确定”“实验初值”“待验证”或“已替代”。重大决定记录问题、结论、理由、替代方案、影响与日期，直接放在负责该问题的文档中。产品文档负责行为，技术方案负责机制，本文负责工作方式，README 负责当前命令；各处引用负责文档，避免复制成多套规则。

旧评审保留历史上下文，已替代内容以当前决定为准。发现文档与代码冲突时，核对当前证据和已确认决定，修正过期内容，不能默默选择方便的一方。

## 2. 任务、交付与完成标准

任务记录可放在 issue、PR 或当前工作记录中，小改动不强制创建额外工单。开工前写清目标、范围、验收方法与已知依赖；探索任务也要明确要回答的问题。

```text
目标与依据：要解决什么，关联哪条产品约定或技术决定
范围与排除项：本次改变什么
验收方法：预期行为、检查命令、设备或实验
依赖与待验证项：阻碍哪些操作，哪些工作可独立继续
交付记录：改动、评审、实际验证结果、证据位置、剩余限制
```

按一个可验证的行为或模块拆分任务，先完成真实交火链路，再扩展全部产品流程。一次提交不混入无关功能、全仓格式化或依赖升级。

联网实现的阶段范围、独立测试方案和状态统一记录在[分阶段实施计划](online-implementation-plan.md)。每阶段先细化测试方案，再实现、运行累计回归和本阶段必需检查，检查最终差异并归档证据；全部退出条件满足后再进入下一阶段。未执行或缺少环境的必需检查不算通过，也不能留到下一阶段补验。已有授权内的阶段通过后自主继续，不逐阶段重复索取确认。

| 状态 | 必须具备的依据 |
| --- | --- |
| 可以开始 | 目标、范围与验收方法明确，影响当前操作的产品决定已解决；技术未知可作为实验目标 |
| 实现完成 | 本次代码和必要文档齐备，完成差异检查；尚未执行的验证明确列出 |
| 验证通过 | 本任务要求的检查已实际执行并通过，记录命令、环境、结果与证据；不能包含未执行的必需项 |
| 体验验收通过 | 涉及的真实设备、网络和操作场景已经完成；纯文档任务无需此项 |
| 已集成 | 变更已评审并集成，集成后的必要检查通过 |
| 可以发布 | 发布范围所需验收、版本、产物、配置与回退准备齐备 |
| 已发布 | 已在授权目标部署，并取得部署后的检查结果 |

报告使用实际达到的状态。已提交或已合并不等于已验证，测试通过不自动构成发布授权。阶段验收不能用后续阶段会补齐的必需证据代替；缺少真机或目标服务器时，准确停在已完成的层级。

## 3. 目标目录与模块边界

以下路径相对仓库根目录。按职责逐步提取，目录在有实际模块时创建。

```text
src/
  sim/                    共用游戏计算
    maps/                 布局、碰撞定义、出生点、据点
    modes/                团队竞技、中继争夺规则
  protocol/               消息格式、版本、编解码
  net/                    浏览器同步、时间采样、预测与插值
  client/
    entries/              online.js、offline.js 两个明确入口
    sessions/             本地与联网会话适配
    input/                键鼠、触屏、焦点与横屏提示
    view/                 渲染、模型、镜头、声音、特效
    ui/                   菜单、大厅、HUD、结算
    lab/                  展示场
server/
  main.js                 源码启动入口
  app.js                  创建与关闭服务
  config.js               服务端配置读取与校验
  rooms/                  房间、成员、接纳与角色更替
  transport/              HTTP、WebSocket、连接与发送队列
  sync/                   输入消费、快照提取与回溯历史
tests/
  sim/ protocol/ net/ server/ integration/
scripts/                  测试驱动、诊断与构建辅助
docs/                     产品、技术、规范与验收摘要
offline/                  带版本的离线发布文件
artifacts/                原始日志、截图、实验数据，忽略提交
dist/                     构建产物，忽略提交
build.mjs                 构建总入口
```

| 模块 | 职责 | 允许依赖 |
| --- | --- | --- |
| `sim` | 移动、碰撞、武器、伤害、命中姿态、AI、计分、对局流程 | 本模块与无设备副作用的数学计算 |
| `protocol` | 消息数据定义、协议版本、结构校验和编码解码 | 本模块；仅 `blocks.js` 可导入锁定的 `fflate/browser` 做有界块编解码；可用 JSDoc 引用领域类型，不运行模拟 |
| `net` | 浏览器连接、时间同步、输入历史、预测重放和远端插值 | `sim`、`protocol`、浏览器通信与时间 API |
| `client` | 输入、界面、表现与会话装配 | `sim`、`protocol`、`net`、浏览器表现库 |
| `server` | 房间、连接、调度、同步和历史管理 | `sim`、`protocol`、Node.js 与服务端通信库 |

`sim` 不导入其他运行层，不访问 DOM、WebGL、材质、声音、文件或网络。`protocol` 不导入运行层，不实例化对局。浏览器代码与服务端代码不互相导入，不允许循环依赖或通过全局对象绕开边界。跨模块只使用明确导出的接口，具体文件职责在提取时确定，不预先建立空的抽象层。

上述 fflate 例外来自已授权的[带宽优化](online-bandwidth-test-results.md)：锁定0.8.3、MIT、纯字节计算，块与总展开量有界；不开放 `protocol` 的其他第三方导入。模块检查同时验证该正例与其余拒绝边界。

地图布局由 `sim/maps` 唯一提供，浏览器读取布局生成画面。影响命中盒的骨骼计算归 `sim`，模型与纯视觉动作归 `client/view`。预测算法归 `net`，被重放的移动和武器计算归 `sim`。回溯历史归 `server/sync`，射线、遮挡、穿透和伤害规则归 `sim`。

## 4. 状态所有权与接口

对局核心持有并修改角色、武器、比分、模拟时间和对局阶段。服务端房间持有成员、连接关联、密码与容量，通过核心接口改变对局；不能另建独立的比分或流程状态机。恢复倒计时由宿主单调时间驱动，通过核心接口完成阶段切换；离线恢复保留原体验。

联网浏览器分别保存权威副本、本人预测状态和显示状态。画面平滑坐标不能直接用于预测碰撞，事件不能在快照之外再次扣血或计分。远端真人与机器人的可命中姿态完全来自配对快照与共用姿态计算，不能被即时事件重复修改。

每个房间独立拥有动态状态、输入队列、事件、历史与查询工作缓冲。跨房间只共享能证明只读的数据；不能共享含搜索标记或临时数组的完整可变实例。

会话统一提供提交输入、配装、暂停、恢复、退出，以及状态和事件通知。开始本地对局与创建、加入联网房间使用各自实际能力；离线会话直接调用核心，不构造虚假网络消息或延迟缓冲。

公共接口使用 JSDoc 说明参数、单位、返回值、错误、状态修改权和生命周期。输入、公共快照、本人校正与事件分别定义数据结构，普通数据不能携带连接、材质或完整游戏实例。预测状态的保存、恢复和重放共用同一份字段定义，逐项标记恢复或重新推导方式。

## 5. 代码、时间与资源

- 继续使用 JavaScript 与 ESM。运行时代码用 `.js`，构建与测试脚本沿用 `.mjs`，不同时开展 TypeScript 迁移。
- 文件名用 `kebab-case`，类名用 `PascalCase`，函数和变量用 `camelCase`，固定常量用 `UPPER_SNAKE_CASE`。
- 新代码使用两空格缩进、单引号和分号；按职责展开控制流，不把多个状态变更挤在一行。格式工具只处理本次涉及文件。
- 函数和模块按职责拆分，不设任意行数上限；新增通用层必须有当前明确的使用者与收益。
- 模拟步长和规则时间使用秒，网络时间字段使用 `Ms` 后缀，步编号使用 `Tick`，输入和事件序号使用 `Seq`；角色身份、生命和输入阶段分别命名。
- 核心的时钟和随机源由宿主提供；影响规则与预测的代码不直接使用系统日期、`Math.random()` 或定时器。视觉随机源与规则随机源分开。
- 三维坐标、朝向和单位沿用现有约定；提交前核对射击起点、后坐力、受击偏转、下蹲和命中盒，不能在提取时悄悄更换规则。
- 导入模块不启动监听、对局、浏览器连接或循环。入口负责装配，创建资源的模块提供明确释放方法。
- 可变状态和缓存属于实例。连接、定时任务、订阅、历史与 GPU 资源随对应生命周期释放，重复关闭应安全。
- 预期失败返回稳定的错误码，由界面转换为提示；配置错误应在启动时明确失败。不能吞掉错误后假装操作成功。

## 6. 启动、构建与环境

### 6.1 环境基线

后续开发与服务端发布采用 Node.js 24.x、npm 11.x，验收记录精确补丁版本。该选择沿用当前工具链，Node.js 24 仍处于 [LTS 支持期](https://nodejs.org/en/about/previous-releases)。升级主版本作为独立变更验证，不自动追随最新主版本。此开发基线不改变离线文件的浏览器要求。

依赖由 `package.json` 与 `package-lock.json` 一起管理。日常复现与构建使用 [`npm ci`](https://docs.npmjs.com/cli/v11/commands/npm-ci/)，不通过删除锁文件解决安装问题。新增依赖记录用途、许可与运行时或开发时归属；升级与功能改动尽量分开。

源码、测试、工具、JSON、CSS、Markdown 与源码 HTML 统一 LF，由根目录 `.gitattributes` 固定检出策略，Prettier 显式设置 `endOfLine: 'lf'`，不依赖开发者全局 `core.autocrlf`。历史离线发布 HTML 沿用原策略，不顺带转换。新电脑的安装、Git 配置、验证及项目上下文见[续接指南](development-continuation.md)。

安装、测试、构建和启动命令从仓库根目录执行。脚本通过自身位置定位资源，不依赖开发者的用户目录。跨平台浏览器测试统一支持 `CHROME_PATH`，缺少浏览器时提示如何配置；浏览器路径、测试服务地址与网络注入前置条件写入实际运行说明。


S2 已接入下表的构建、源码与产物启动入口。`npm start` 现运行 S4 房间与完整玩法，旧静态预览保留为 `npm run preview:offline`，`dist/index.html` 保留为离线回归兼容文件。S4 实现和自动化记录见[阶段状态](online-implementation-plan.md#9-状态与交付记录)；实机体验和发布准备仍未全部通过。S1 已接入递归测试发现、工程检查与浏览器路径配置；实际命令见 [README](../README.md#运行)。

### 6.3 实施后的入口和命令合同

服务端源码入口固定为 `server/main.js`；它只读取配置、调用 `server/app.js`、监听和处理退出。`app.js` 提供可创建、可启动、可关闭的应用，导入它不能占用端口。浏览器入口为 `src/client/entries/online.js` 和 `offline.js`，分别装配联网与本地会话。

| 目标命令 | 实施后行为 |
| --- | --- |
| `npm run build` | 构建在线页面、离线单 HTML、服务端和发布清单 |
| `npm run build:online` / `build:offline` / `build:server` | 分别构建对应目标，单目标产物不冒充完整发布 |
| `npm run package` / `package:release` | 全量构建独立运行 ZIP、清单和校验值；后者额外要求干净正式来源，不代表已验收或已部署 |
| `npm start` | 执行 `node dist/server/main.js`，同进程提供在线页面与 `/ws` |
| `npm run dev` | 监听源码变更运行 `server/main.js`，使用已构建页面；缺页面时明确提示先构建 |
| `npm test` | 自动发现根目录和分组目录内的测试，测试自行创建和关闭临时服务 |
| `npm run test:browser` | 根据明确配置运行浏览器回归，说明受测地址与目标构建 |
| `npm run check` | 格式、静态规则、循环依赖与模块导入边界检查 |

完整构建产物固定为 `dist/online/index.html`、`dist/offline/harbor-after-rain.html`、`dist/server/main.js` 和 `dist/release.json`，并携带运行 `package.json`、锁文件、校验器与说明。服务端按 Node.js ESM 构建，共用计算纳入产物，运行时外部依赖随锁文件交付。独立包只安装锁定的 `ws`；源码依赖与运行依赖的版本、完整性记录须匹配，升级时同步维护，不能手工删改锁文件来绕过检查。离线文件包含全部必要资源与许可，不连接服务器。交付目录、来源模式与核验细则见[发布与运行约定](release-runbook.md#3-构建与产物)。

命令切换、测试发现、格式和边界检查在相应模块的首批实施中交付，同时更新 README。新建测试子目录前必须先扩大测试发现范围。联网入口可运行前，现有 `npm start` 保持静态预览；切换时将原用途保留为 `npm run preview:offline`。

自动检查接入 CI 后，合并要求其通过；接入前保留本地可复现命令和证据，不能把尚未存在的 CI 标记为通过。

## 8. 测试、验收与证据

### 8.1 先设计覆盖，控制用例数量

尽量用少量、稳定且覆盖明确的用例验证功能。**原则上不新增测试用例：先复用、加强或合并现有用例；只有存在明确的功能或验收需求、缺陷回归需求，或已确认需求中有证据的关键覆盖缺口，且现有用例无法合理承载时，才新增。没有明确依据，不新增用例。**

新增前在测试方案或变更说明中写清需求或缺陷依据、现有用例为何不足、预期增加的覆盖。此记录用于工程判断，不增加逐条向用户请求批准的流程。新增参数变体也须说明增量覆盖与运行成本，不能通过参数化或把多个场景塞进长脚本隐藏数量增长。简单可逆的文案、样式或纯重构不因代码有改动就新增用例。

设计时先将已确认功能、关键状态迁移、边界及失败路径映射到现有证据，再选择必要的补强。覆盖表使用以下字段，可直接放在阶段测试方案中，不另建重复台账：

```text
功能或状态边界 → 责任层 → 现有用例与直接/间接证据 → 缺口 → 复用、加强、合并或新增及依据
```

每条具体用例有明确的主要验证目标，失败后能独立定位；场景组只作覆盖目录，不规定必须凑齐多少条。关键限制检查窗内、边界和窗外，普通参数选代表值，必要组合针对已知风险选择。关键行为和边界取得直接证据、其余缺口明确列出后，不再为同一结论重复增加用例。用例数和代码覆盖率不单独作为完成目标。

合并、替换或删除重复、过时用例时保留有效断言、缺陷回归及需求映射；不能为减少数量或消除失败而降低验收标准。单条用例的最小记录如下，环境和证据由测试工具统一补充：

```text
编号与需求依据 → 责任层 → 初始状态与输入 → 操作及检查点 → 预期结果与容差 → 独立运行方式
```

### 8.2 按责任分层，协议独立成组

测试按共用规则、服务器、客户端和集成四层组织；跨端协议另设可独立运行的契约测试组。

| 层或组 | 主要责任 | 依赖边界 |
| --- | --- | --- |
| 共用规则 | 移动碰撞、武器、AI、命中姿态、伤害、比分和对局阶段规则 | Node.js 中运行实际核心，不启动服务或浏览器 |
| 服务器 | 接纳与调度、输入消费与确认、核心接口调用、成员与快照、连接隔离和释放 | 按需自建临时服务，不依赖浏览器操作 |
| 客户端 | 输入采集、预测校正、插值、显示引用、反馈去重和界面状态 | 逻辑测试由固定快照和事件驱动；界面测试使用浏览器；不依赖真实服务器准备状态 |
| 集成 | 实际输入、协议、服务端处理、快照及客户端展示的连接处 | 自建临时服务与浏览器或实际协议客户端，只保留必要的完整链路场景 |
| 协议契约组 | 编解码、结构与范围校验、版本兼容、错误消息 | 不运行对局；客户端消息样本须符合真实协议，跨端衔接由必要的真实连接检查验证 |

每个用例按主要被测责任归属。规则在较低层验证，集成层检查连接处，不把同一套参数组合在每层完整重写。共用代码只保留一套实现，各层测试分别核对自己的调用和行为。

### 8.3 每条用例可独立运行

- 支持按稳定编号或名称选择单条、整层或全套运行，单条有完整命令。选择未命中应明确失败；未选中的用例不计为已验证。当前可用入口以 README 为准，未落地的分层或单条入口不能描述为已具备。
- 用例自行建立状态，明确种子、时间、输入和消息序列；不依赖执行顺序、上条用例的房间、缓存、文件或人工预先启动的服务。临时端口、文件和输出目录相互隔离。
- 创建的连接、服务、定时器、订阅和浏览器上下文在成功、失败或超时后均清理，并设置有限的启动、执行及清理超时；只清理本用例拥有的资源。构建可在一轮测试中复用，但先核对来源、配置和产物标识，缺少前置条件时自动准备或明确给出准备命令。
- 独立运行不要求全部并行；浏览器和共享设备可串行。控制测试运行时长，避免用真实等待替代可控逻辑时钟；异步检查等待明确状态，固定等待只用于实际需要验证的时间行为。

### 8.4 断言依据、过程检查与替身边界

- 预期结果来自已确认规则、明确计算或可信基线，优先检查可观察行为与公开接口。两端使用同一函数比较相等，只能证明一致性，不能独自证明正确性；关键结果另有独立依据，数值容差在运行前确定。
- 同时检查必要的过程约束和最终结果。例如预测校正既核对恢复状态，也核对未确认阶段、扣弹、射击、声音和计分次数；不能只在最后恢复权威状态后比较相等，或只检查“发生过命中”“没有报错”。关键断言应能区分预期行为与典型错误。
- 替身只控制被测责任之外的时间、网络或设备入口，不替换要验证的规则或算法。可设置起始站位、消息与故障条件，被测动作仍走实际调用链；测试恢复倒计时时不能直接改成目标阶段绕过恢复逻辑。替身验证的结论单独标明，不能代替对应的真实集成证据。
- 可复现缺陷先确认原场景能失败，再用相同场景验证修复；优先补强现有用例，确需新增时遵循 8.1 节。契约变更后同步维护样本和断言，不复制另一套复杂游戏实现充当预期。

### 8.5 按改动范围选择必要检查

| 改动范围 | 必要验证 |
| --- | --- |
| 文档与规范 | 链接、命令现状、交叉引用及产品约定一致性 |
| 模拟、规则与姿态提取 | 实际共用代码的单元与场景测试；对应离线入口行为对照 |
| 编解码与输入调度 | 有效及错误数据、执行或作废确认、队列上限、生命周期边界和往返精度 |
| 预测、插值与回溯 | 确定序列回放、远端事件先到、引用失效、自动连射缺输入；两台真实设备交火 |
| 房间与流程 | 并发加入、最后位置、角色更替、断线、暂停恢复、结算一次及房间隔离 |
| 界面、输入与表现 | 浏览器真实操作；涉及触屏、旋转、声音与系统能力时补对应真机观察 |
| 发布候选 | 技术方案验证矩阵、受支持设备实测、目标服务器容量与离线独立运行 |

已有有效证据按实际影响复用。规则、依赖、配置或最终产物改变后，重跑受影响检查；文档变更检查链接与一致性，不机械重跑无关游戏测试。

### 8.6 执行结果与证据

报告区分通过、失败、超时、环境不可用、跳过及未执行。必需项超时、缺环境或跳过均不算通过；自动重跑成功不能抹去首次失败，须保留失败记录并定位原因。失败输出包含用例编号、构建、种子、模拟步、必要的输入或消息编号及状态差异，足以独立复现；日志按第 12 节控制数据范围与数量。

浏览器模拟不等同于真机；程序化快进不代表实时性能；WebSocket 延迟包装不代表真实丢包。模拟、自动化、人工与真机证据分别标明。不能以改测试期望的方式掩盖产品回归。

任务明确暂缓的实机或其他检查单列为待验证，不计入本轮自动化通过结果，也不因此视为已满足既有体验或发布门槛。设计规则与测试入口是否已经落地分别记录，规范更新本身不代表现有用例已完成改造。

从首轮基线开始记录设备、OS、浏览器与版本、分辨率及输入方式；覆盖现有桌面键鼠和手机横屏触屏范围。联网阶段按技术方案执行 RTT 0/50/100/150 ms、抖动与真实丢包，以及 60/30 Hz 两档。未验证的浏览器或版本明确标注，不凭空承诺最低支持版本；改变已支持范围先讨论。

原始结果放在 `artifacts/<任务或版本>/`，摘要放在任务记录或版本验收记录中。摘要至少包含构建或提交、未提交差异标识、环境、配置、命令、场景、预期与实际结果、证据位置和未验证项。发布所依赖的原始证据须随交付归档或提供稳定可访问位置，不能只留下另一台机器上不可访问的路径。

## 9. 缺陷处理与重新审视

| 等级 | 判定与处理 |
| --- | --- |
| P0 | 跨房间串扰、全服失效或数据与权限边界被破坏：优先止损，停止相关发布 |
| P1 | 核心对战、输入、命中、计分或离线交付失效：阻止受影响版本发布 |
| P2 | 有可用路径的局部功能或明显体验问题：记录影响，排入近期任务 |
| P3 | 低影响的表现与文案问题：按用户价值排序 |

缺陷记录包含版本、环境、复现步骤、预期与实际、影响及证据。先区分网络、规则、姿态和表现问题，再提出可检验假设；必要时查官方文档、标准、上游源码和同类产品。每次尝试应产生新信息。

多种合理路径失败、没有新证据、特殊分支持续增加或中间目标偏离用户价值时，停止当前路径。在同一问题框架内尝试第三种不同变通前，重述目标，分开明确要求与新增假设，比较简化、替换、延期和人工验证，依据最高价值路径继续。只在需要改变已确认边界或不存在明显优选时讨论产品取舍。

修复关闭前完成原复现及相关回归。暂时无法复现的缺陷保留证据和状态，不标为已修复。发布后发现的问题关联引入与修复版本，保留已知问题和适用的临时操作说明。

## 10. 性能实验与优化

每次实验明确问题、基线、变量、构建、设备、配置、数据和判断。比较相同必要状态的编码方案，不用缺字段的小包声称优化收益；不从截图 FPS 推断服务器容量。

按技术方案记录消息真实字节、总出网、积压及持续时间、RTT、快照间隔、校正幅度、每房间与全进程步进分位数、调度落后、事件循环延迟与内存。检查创建尖峰、高机器人占比、慢连接与释放后的稳定性。

当前固定 60 Hz 模拟和 60/30 Hz 两档同步。缓冲、回溯窗口、输入超时、队列上限和机器容量仍需实测。先保证规则与姿态正确，再针对证据中的热点优化；复杂差量、通用压缩、替代传输、姿态降频或多进程按技术方案的进入条件处理。

开放试玩前必须记录可接受的网络体验范围、校正和停顿判断、固定容量、队列阈值及其测量依据。对主观手感使用具体试玩场景记录；证据不能区分明显优选时，提出具体对照供用户判断，不先承诺任意数值。

## 11. 版本、配置与兼容

| 标识 | 用途与变更规则 |
| --- | --- |
| 产品版本 | 使用 `major.minor.patch`；新增联网等能力提升 minor，兼容修复提升 patch，明确破坏使用合同的变化提升 major |
| 构建标识 | 精确追溯提交和构建配置；本地未提交构建带差异标识，不用于正式发布 |
| 协议版本 | 消息结构或消费语义不兼容时递增；首版不维护跨协议兼容层 |
| 规则标识 | 从影响权威模拟的规则、地图碰撞与计算版本生成，排除音量、画质等个人设置 |

同一发布的在线页面、服务端和离线文件使用同一来源与产品版本。首版联网连接要求构建、协议和规则匹配；不匹配明确要求刷新或重新下载，不能静默混用。每次发布保留清单、校验值、配置与已知限制。

共用规则集中在 `src/sim`，服务端运行参数集中在 `server/config.js`，浏览器个人设置归 `client`。服务端环境变量覆盖已声明默认值，启动时一次校验；不自动读取未声明的本机文件。客户端只接收运行所需的规则与同步配置，不读取服务端环境。

配置项写明名称、类型、单位、范围、默认值与是否需重启；容量和队列参数必须有有限上限。首版通过启动配置调整，不引入隐含热更新。机器地址、浏览器路径和凭据不写入源码；新增本机配置文件前先确定忽略规则，公共示例只含说明与无敏感性的样例。

## 12. 日志、数据与素材

日志区分错误、警告、信息和调试。运行记录包含构建、配置摘要和房间／连接临时编号；射击诊断关联输入、射击、角色、生命、阶段、样本及判定路径。调试采样默认关闭，启用时限制持续时间、数量与内存，不为每个模拟步无界写盘。

房间密码、凭据、完整报文和无需诊断的昵称、地址不进入常规日志。当前不增加账号、长期玩家档案或第三方遥测。日志和诊断数据默认只在本机或自有服务器处理；需要导出时去除无关个人信息，改变收集或共享边界先讨论。

首版运行日志按文件轮转，保留最近 7 天且总量不超过 100 MB，先达到任一上限就清理最旧文件；独立于系统日志的其他保留策略，部署前一并核对。发布与验收证据单独归档，至少保留当前和上一可回退版本；不把完整运行日志永久归档。调整这些工程上限记录理由，不扩大数据用途。

新增依赖、模型、声音、图片和参考素材记录来源、用途、版本及许可要求。保留既有署名和构建中的许可文本；参考原文件与临时诊断素材不因被本机读取就自动纳入发布。来源或可分发条件未确认的素材先留在发布范围外。

## 13. 发布、维护与当前执行范围

发布、健康检查、停止、故障处理和回退按[发布与运行约定](release-runbook.md)执行。首版采用单机完整版本替换，重启结束内存对局；不承诺热更新、房间迁移或对局恢复。

运行反馈按缺陷或明确改进任务进入第 2 节流程。维护变更仍需证据与回归，运行日志不能自动成为新增产品需求。

模块边界、入口、工作流程和证据要求已经确定。S1 已交付锁定版本的 Prettier/ESLint、递归测试发现、循环与模块边界检查；新核心和小型适配层执行格式与静态规则，大型旧模块保持局部修改并检查语法，不全仓格式化。发布清单、完整会话装配和联网运行能力仍在后续阶段交付；具体实现及验证结果以阶段记录为准。
