# TCP恢复首轮对照记录

2026-11-15，按[方案](online-tcp-recovery-optimization-plan.md)完成三个有效30Hz短断网窗口。**服务器RTO下限100ms在本轮变慢；客户端ACK调整缩短了一段等待，但未改善新输入真正执行的时间。生产参数保持，不继续扩展参数或种子。** 本轮是单次筛选，原O4相对弱网门槛仍待验。

## 1. 范围与可复现证据

复用S3-E2，ingress/IFB、TCP包头归因、种子4207、原2秒预热和8秒采样，约900ms双向全丢包。按baseline→server-rto100→client-ack10顺序执行，未组合。每组保留原活动、移动/开火、旧输入作废、反馈、绝对质量、队列和清理断言；三组均通过。没有新增永久用例。

环境为Node24.18.0、Linux6.18.33.2/WSL Ubuntu-26.04，普通应用用户wandc；root仅负责临时netns配置和抓包。协议9、构建`cb7ca0d43a94fea96e07d8322b4eb42b3d74ad1c3e4f8c8575ce8c4c28a9ff22`，与开工相同。设置前核对四个socket的端点，设置后逐项读回，仅指定选项改变，其余端点与sysctl保持；宿主默认值前后相同。

证据根目录：[tcp-controls](../artifacts/online-weak-network/20261115/tcp-controls/)。[登记](../artifacts/online-weak-network/20261115/tcp-controls/registration.json)、[汇总](../artifacts/online-weak-network/20261115/tcp-controls/comparison.json)及其可重算脚本summarize.mjs均保留。有效原始目录：

- `measured/baseline/S3-E2-30-interruption/`
- `measured/server-rto100/S3-E2-30-interruption/`
- `measured-ack-rounded/client-ack10/S3-E2-30-interruption/`

每个目录包含report.json、kernel.json、observations.json、tcp-headers.json、transport-attribution.json。捕获丢包均0，全部241个已应用常规状态均有发送/ACK映射。ACK时间指接收端发出的TCP确认，操作确认另列，均不以应用send时间代替。

复现单组命令如下；MODE取baseline、server-rto100或client-ack10，OUT必须选未使用目录，命令在Windows桌面用户上下文执行：

```powershell
node scripts/s3/run.mjs --case=S3-E2 --hz=30 --profile=interruption --topology=ingress --trace=tcp --seed=4207 --user=wandc --tcp-tuning=MODE --out=OUT
```

该选项默认none，且只允许上述明确的30Hz短断网诊断范围。它不接入服务器启动或生产配置。ACK夹具只读`/proc/config.gz`核对实际内核粒度；没有该能力就明确失败。

## 2. 参数作用域与平台差异

| 组别 | 唯一请求变更 | 实际读回 | 包头/ss旁证 |
| --- | --- | --- | --- |
| 基线 | 无 | 四端RTO下限200ms、ACK上限200ms、RTO上限120s | 首个服务器RTO样本208ms |
| 服务器RTO | 受损服务器TCP_RTO_MIN_US=100000 | 100000us；另外三端及其他选项不变 | 首个服务器RTO样本108ms；重试节奏实际改变 |
| 客户端ACK | 受损客户端TCP_DELACK_MAX_US=10000 | **12000us**；另外三端及其他选项不变 | 客户端ss的ato首样本12ms；首状态后的纯ACK提前 |

当前CONFIG_HZ=250，每个jiffy为4ms。Linux把该选项转成jiffy保存，10ms请求向上取整为12ms；夹具根据只读内核配置推导精确预期值。[Linux6.18实现](https://raw.githubusercontent.com/torvalds/linux/v6.18/net/ipv4/tcp.c) 基线200ms是上限，不能把它说成实际每次等200ms；实际等待见下表。

失败记录全部保留：首次三组在参数设置/预热前因普通用户不能读取root的`/proc/1/ns/net`被拦住。修正为隔离环境设置进程传递已核实的标识，应用独立核对自身netns，仍以普通用户运行。随后ACK组设置成功，但原夹具误要求读回精确10000而在预热前失败；核实粒度后仅补跑该无效窗口。四次失败均无采样窗口，资源清理完成，不计作有效实验，也未挑选成功的有效样本替换失败结果。

## 3. 恢复分解

单位ms。恢复耗时均从tc实际恢复完成计时；实际全丢包时段为912.47/902.55/907.87ms，调度差异保留，未按假定900ms校正。新鲜状态仍要求连续3个不同常规tick均在原50ms年龄范围内，以第三个完整状态为准。

| 指标 | 基线 | 服务器RTO 100ms | 客户端ACK 请求10/有效12ms |
| --- | ---: | ---: | ---: |
| 恢复→缺口重发 | 597.38 | 797.92 | 611.52 |
| 恢复→首完整状态 | 597.96 | 798.65 | 612.11 |
| 首完整状态→首个推进ACK | 43.46 | 47.28 | 15.43 |
| 首完整状态→当时积压排空 | 56.51 | 55.04 | 28.27 |
| 恢复→3个新鲜状态 | 689.86 | 904.03 | 661.16 |
| 恢复→新输入真正执行 | 873.84 | 902.16 | 875.70 |
| 恢复→该执行输入获确认 | 892.55 | 904.03 | 891.76 |
| 真实时间加权状态年龄p99 | 1504.77 | 1699.74 | 1490.48 |

RTO参数确实生效，却碰到更差的退避相位。基线同一缺口的重试在采样后2225.15、2649.14、3513.14ms；RTO组变为2135.89、2355.88、2803.87、3703.87ms。最后一次恢复前重试早于恢复102.08ms，下一次要再等797.92ms。更低下限没有带来本轮收益：新鲜状态慢214.16ms，新输入执行慢28.31ms。因此停止该候选，不自动进入0.7/1.1秒相位或其他参数矩阵；本轮也不推断100ms在所有网络下必然更差。

ACK组首个推进确认在三组中均是**纯ACK**，不是应用回包携带ACK。调整后这段等待少28.03ms，积压排空少28.25ms，新鲜状态早28.70ms。但缺口重发仍等611.52ms；新输入执行相差+1.86ms，执行确认相差−0.80ms，未观察到操作恢复收益。

反向TCP继续等待重传：恢复后上行首次重发分别在849.38/861.92/835.52ms；三个窗口的受损端新鲜输入消费数均343。这与“仅降低接收状态的ACK等待，不能重设客户端发送方向的退避”一致。观察不等于严格因果隔离：同一种子不能固定全部TCP分段、内核定时和应用调度。

ACK组多11个客户端纯ACK，重传包数没有减少。RTO组字节更少不能解读为压缩收益：该组游戏与反馈进展、压缩历史也随恢复时序变化。健康端均应用241个状态，保持约30Hz、无显示时间倒退，原健康端质量检查通过。ACK组最大间隔与事件循环最大延迟增加，单次窗口不足以将其归因为参数或声明长期无副作用。

本轮记录步进/发布耗时、事件循环与RSS，**没有采进程CPU占用率**，不能宣称CPU开销不变。工程检查95个格式/规则文件、99个运行模块通过；三个Python夹具AST检查通过；汇总脚本独立核对四端参数、身份一致、抓包与原验收。运行源码、全部既有测试、包/构建配置保持开工哈希，复用此前199项累计、构建、浏览器及容量证据，本轮未重复执行这些未受影响检查。最终范围与校验记录见证据目录source-audit.json。

## 5. 决定与剩余事项

本轮只增加默认关闭的实验夹具与记录，生产参数、同步率、消息、重试/退出合同保持。RTO候选本轮没有净收益，停止继续调参；ACK候选保留诊断收益，但浏览器页面不能设置该socket选项，不能直接产品化或声称真实浏览器收益。没有自动实施发送窗口、额外反馈消息、组合参数或传输迁移。

原O4相对门槛未重跑或替换，仍待验。目标Linux服务器、真实浏览器TCP栈、双设备与主观体验没有本轮证据；未进入S6，未提交、推送、部署或发布。
