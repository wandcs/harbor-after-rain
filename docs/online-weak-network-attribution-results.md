# 弱网重传与旧快照积压归因

日期：2026-11-15。依据[事前设计](online-weak-network-test-plan.md#后续重传恢复与旧快照归因)。用户授权复用丢包/短断网用例量出等待来源，再决定发送窗口，并补压缩等级勘误。

**本轮建议暂不实现通用发送窗口。** 短断网的主要等待发生在下一次缺口重发之前；丢包下确有最多约45ms的后续发送等待，但同时受ACK/拥塞恢复影响，尚不能当作窗口的确定收益。原O4相对弱网指标仍待验。

运行Windows Node24.18.0、WSL Ubuntu-26.04。应用为普通用户wandc；root只在临时netns设置网络与采包头，退出销毁。复用ingress/IFB、MTU1500、关闭GRO/GSO/TSO、种子4207：60Hz无故障校准、60Hz loss、60/30Hz interruption，共4个原8秒窗口。loss仍为单程50ms加双向1%随机丢包；interruption仍约0.9秒全丢包。

4窗均通过原年龄/间隔、健康端、权威移动/开火、无补执行、去重、队列和清理断言。95个格式/静态文件、99个运行模块检查通过，Python AST校核通过；产品源码与构建标识一致。本轮没有重新跑容量或设备矩阵。

## 2. 测量如何互证

Python标准库AF_PACKET只保存端口45931的出站TCP包头元数据，不落盘业务载荷；SYN给出两个方向的字节基准。驱动外围记录快照生成、Outbox交付send、WebSocket实际字节区间，逐条核对无掩码/无PMD帧长度与socket.bytesWritten。每个测量窗内成功应用的快照均对应到已发送、已被TCP确认的完整字节区间。

出站数据包证明发出；接收端生成的累计ACK/SACK说明其接收进度或缺口，再用实际消息入口/完整应用时刻交叉检查。接收抓包点不能直接当作应用交付；ACK也可能延迟。方法依据：[Linux packet接口](https://man7.org/linux/man-pages/man7/packet.7.html)、[内核时间戳](https://man7.org/linux/man-pages/man7/socket.7.html)、[SACK规范](https://www.rfc-editor.org/rfc/rfc2018.html)。

| 配置 | 捕获包头 | 映射成功应用快照 | 捕获丢包 | 实时/单调换算漂移 ms |
| --- | ---: | ---: | ---: | ---: |
| 60Hz无故障 | 1419 | 481 | 0 | 0.000069 |
| 60Hz丢包 | 1498 | 480 | 0 | 0.000045 |
| 60Hz短断网 | 1311 | 481 | 0 | 0.000085 |
| 30Hz短断网 | 1201 | 241 | 0 | 0.000015 |

无故障没有观测到重传或SACK缺口。ACK可能晚于应用交付，无故障最大约10.82ms；30Hz断网恢复时约43.37ms。因此不能把“等到ACK”的全部时间算成重传或网络交付。内核时间戳换算、捕获零丢包和数量上限均已检查；原始记录可复核。

独立calculation-check.mjs用手算时间/字节序列检查缺口、重发、排空、TCP序号回绕、捕获缺失拒绝及预热边界。归因器首版把没有测量期应用行的预热快照误算为待处理；序号互证发现后，按开始时已应用序号及窗口内单调进度修正，补手算反证，用相同原始记录重算，没有换种子或重跑挑结果。

## 3. 短断网：大头在下一次重发之前

下面各列按实际先后时间拆分，同一行可以相加得到最后一列。后半段仍包含ACK、发送、交付和应用，不能全部叫作纯队列成本。

| 同步Hz | tc恢复→缺口重发 ms | 重发→首个完整快照 ms | 首个快照→当时已提交快照排空 ms | 排空→3个新鲜tick确认 ms | 恢复总时长 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 60 | 594.08 | 0.65 | 15.80 | 0.07 | 610.61 |
| 30 | 616.52 | 0.61 | 49.88 | 27.40 | 694.42 |

60Hz：同一个缺失字节的重发发生在测量开始后2221.79、2641.79、3509.80ms；链路在2915.72ms已恢复，直到3509.80ms才再次重发。30Hz对应2225.02、2665.01、3529.04ms，链路2912.52ms恢复。两个方向的包头都保留，不以一个方向的发送代替另一方向的进展。

恢复后的ss样本均显示服务器`rto:832 backoff:2 cwnd:1`。这与重复字节范围及首个完整快照时刻共同说明：本轮约594/617ms主要在等退避后的重传，不是浏览器时钟误差或仍在执行旧操作。全丢包时没有后续字节抵达，不能因为那一段没有SACK就断言没有接收缺口。

30Hz首个完整快照在3529.66ms就已应用，首个推进的ACK到3573.02ms才生成，约43.37ms。剩余旧数据随后约6.52ms排空。49.88ms后半段中，这段ACK推进等待占了大部分；不能把它全部归成旧快照占用带宽。最后27.40ms是三份新鲜tick确认中的剩余等待，也不等于积压成本。

### 队列真实存在，但字节数不能直接换算为可省延迟

| 观察时点 | 60Hz待应用快照数/字节 | 30Hz待应用快照数/字节 |
| --- | ---: | ---: |
| tc恢复完成 | 55 / 36209 | 28 / 18701 |
| 首个完整快照应用后 | 90 / 68205 | 45 / 34641 |

tc恢复时，应用已提交但尚未出现在发送包头中的字节分别33059/15732，另有4875/4693字节已发出、尚未被接收端累计确认。首个快照应用后，未发出的已提交字节为47217/33981。应用socket.bufferedAmount最大仍为0，证明单看该值不能排除内核待发旧状态。

60Hz首个快照后90份待应用状态在15.80ms内排空，其中解码、配对提交、预测校正的累计工作约12.88ms；与TCP发送/交付时间交错，不能另加12.88ms。30Hz相同工作约4.62ms。队列确有成本，但它没有解释前面的约600ms等待。

## 4. 丢包：缺口恢复约一往返，后续要分开看

8秒测量期下行9次、上行7次重复字节发送。接收端观察到9个可完整关联到下行重传的SACK缺口段，每段由首次SACK见到缺口到累计ACK前进为100.11—116.86ms，合计937.82ms。这是接收端见到缺口后的等待，未声称包含更早的首次丢失时刻；也未假定具体使用“三个重复ACK”或某个特定恢复算法。

| 缺口补齐后的观察 | 本轮范围 | 解释 |
| --- | ---: | --- |
| 当时已超过100ms年龄的旧快照排空 | 0.57—1.69ms | 这些陈旧帧主要在补齐后集中应用 |
| 当时全部待应用快照排空 | 49.14—95.04ms | 包含正常在途新状态，不能全算积压 |
| 其中末尾快照尚未首次发出的等待 | 0—45.00ms | 与ACK/拥塞恢复耦合，存在优化空间但不是窗口的确定收益 |
| 末尾快照发出后的剩余交付/应用 | 约49.14—50.65ms | 与该配置正常单程50ms一致 |

每次缺口补齐时仍有10—12份待应用快照，已提交但未发出的字节为0—2485。100ms新鲜度仅为本轮诊断边界（单程50ms加原50ms余量），没有替换原O4门槛。较新的待应用状态也会在随后ACK等待中变老，因此表中“旧帧约1ms排空”不能证明后续所有状态都新鲜。

这里确有最多约45ms的发送等待，值得保留为后续目标；需要同时看到主要的100—117ms缺口恢复，以及正常50ms单程交付。直接相加所有段、或按全部待应用快照数量计算窗口收益，都会高估。

## 5. 发送窗口决定与剩余限制

暂不进入生产发送窗口。它不能取消已经交给TCP的缺失前缀，也不能直接消除本轮占主导的RTO退避；丢包下潜在的0—45ms收益尚与ACK/拥塞控制耦合。可靠的窗口还需新增解码进度、数量/字节/年龄上限、重要消息进展、基准所有权与150ms RTT同步率验证，当前证据不足以证明这些成本的净收益满足方案进入条件。

如果后续专门针对这0—45ms继续优化，应先做可撤的定向原型对照，证明实际新鲜度收益且不减59/29.5Hz成功应用、不延长恢复，再决定正式实现；不把本轮观测当作已完成该原型。本轮到归因与决策为止。

这是指定种子、短窗口和本机隔离拓扑的直接证据，不是公网普遍占比；TCP时序随运行与窗口变化，本轮做同一运行内的时间拆分，不把总恢复时间与前轮的差异当作优化收益。四窗不提供统计显著性或发送窗口的反事实结果。原O4基线/相对年龄未重新改判，目标服务器、实机与体验仍按原安排待验。未修改产品运行代码、部署或发布。

压缩等级的[勘误](online-bandwidth-test-results.md#压缩等级记录勘误2026-11-15)已补齐：冻结参数误记9，最终及现行服务器均level6/memLevel4，原文件和数值门槛不回写。
