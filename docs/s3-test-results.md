## 修复与回归依据

| 问题 | 直接失败证据 | 处理及复验 |
| --- | --- | --- |
| 旧包持续到达掩盖状态超时；本地退出等待底层关闭 | 真实限速下，客户端仍在会话中但权威状态已落后约 9.8 秒；`staleness-red`、`notify-red` | 同时检查接收间隔和权威时间年龄；超时立即通知一次本地退出、清理时钟与缓冲并关闭传输；后续旧消息忽略。6000/6001 ms、重复失败及真实 slow 配置通过 |
| 高 RTT 输入全部迟到 | `rtt150-first`：481 步无有效消费、无实际移动/权威开火；`input-lead-red` | 目标步提前量改为 `max(3, ceil(RTT/2 × 60/1000 + 1))`，继续受 30 步未来窗口约束；四档真实 RTT 操作通过，晚到与过期仍作废 |
| 显示时间线遗漏单程交付 | 150 ms RTT 下全部采样保持端点；`display-buffer-red` | 显示时间减去半 RTT 和配置缓冲；相同链路恢复真实端点插值。对应回溯引用随真实显示更新 |

## 网络结果

实际服务、WebSocket、OnlineSession、Prediction 与显示采样运行于独立 Linux 网络命名空间。只有配置工具使用 Linux root，应用 UID 为 1000；数据包经过内核 netem，健康连接不经过受损队列。采样为无渲染客户端逻辑，不代表真实设备或手感。

`jitter` 是双向各 50±15 ms 正态延迟；netem 的逐包时延变化可能产生重排，因此即使丢包为 0 也观察到 TCP 重传。`loss` 是双向各 50 ms 和独立 1% 丢包，必须同时观察到内核丢包与重传。`interruption` 先停止发输入，再执行约 900 ms 的真实双向断网；表中该项丢包为最终队列计数，断网阶段的单独计数保存在 `blackoutQdisc`，不相加重复计算。

在 0/50/100/150 ms 常规配置中，两档受损玩家都实际移动和产生权威射击，显示采样没有端点保持；这是样本内观察。抖动、丢包和断网仍出现保持及有限回退，报告保留这些退化，没有把它们改成通过阈值。网络配置通过表示正确性、隔离、边界和清理约束成立，不表示已确认对应体验可用。

真实积压采用六名机器人合法死亡状态的完整快照作为负载，保持正常尸体计算与复活。60 Hz 的实际发送积压峰值 **272,469 字节**，超过 262,144 字节阈值后持续约 **2,005 ms**，由服务端结束受损连接，健康连接继续推进。重要消息峰值 16 条、7,895 字节，仍在 128 条/65,536 字节上限内。

首轮试图在 30 Hz 也强求这个分支，但其流量较低、实际发送积压为 0，先触发正常的 6 秒存活检测。该失败来自额外断言对处置顺序的假设。按“较少用例、按责任覆盖”的原则，保留 60 Hz 的真实出站分支与既有共用 Outbox 边界检查；30 Hz 由 slow 配置验证实际隔离和失效处置。`backlog-30-probe` 保留失败，不计为通过，最终 inventory 不包含这个冗余要求。

## 参数与编码结论

| 项目 | 本轮决定及依据 |
| --- | --- |
| 频率 | 模拟/输入仍为 60 Hz，快照固定 60/30 Hz 两档 |
| 显示缓冲 | 保留 33.3/66.7 ms；修正计算时间线，计入单程交付 |
| 回溯实验值 | 默认档由 200 调为 225 ms；150 ms RTT 的调查引用年龄为 204–211 ms。最终正常配置消除了这类不必要的超窗回退；低档保留 250 ms，实测引用约 240 ms。过窗、生命及阶段变化仍回退 |
| 输入新鲜度 | 保留 250 ms；断网期间停止沿用，恢复不集中补射，实际射击间隔仍受固定步武器预算限制 |
| 队列与失效 | 保留输入 64、预测 128、历史 32、重要消息 128 条/64 KiB、发送积压 256 KiB/2 秒、存活 6 秒；实际分支与既有边界检查均有证据 |
| 编码 | 保留 JSON；实验候选只留在 `scripts/s3`，未进入生产传输 |

二进制候选为自包含包内字段字典、int32/float64，无量化、差量或压缩。完整公共/本人状态、尸体姿态、事件、双连接输入及控制样本均计入，两个配置逐值往返相等，数值误差为 0。控制消息为协议夹具，房间状态与事件来自实际核心；不把此 CPU 小样本当作线上公共编码复用后的整房间成本。

| 档位 | JSON / 二进制总字节 | 体积减少 | JSON / 二进制编码均值 μs |
| --- | ---: | ---: | ---: |
| 60 Hz | 8,135,989 / 5,950,764 | 26.9% | 4.73 / 51.06 |
| 30 Hz | 5,714,642 / 4,211,514 | 26.3% | 3.59 / 50.32 |

该候选编码约慢 11–14 倍，解码也更慢，当前没有足够净收益推动生产协议替换。结论限于这个候选与这批数据；继续采用现有公共 JSON 编码复用，不新增依赖或另一套生产格式。
