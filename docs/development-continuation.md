## 2. 新电脑准备与启动

必需：Git、Node.js 24.x、npm 11.x，以及访问 GitHub 和 npm registry 的网络。已实际验证的工具链为 Node.js 24.18.0、npm 11.18.0；其他补丁版本记录后运行相同检查，不自动升级主版本。

在选定的开发目录执行；目录不存在时才克隆。Windows 上遵循桌面用户与沙箱身份约定，常规开发使用普通用户权限：

```sh
git clone --branch codex/online-multiplayer https://github.com/wandcs/harbor-after-rain.git
cd harbor-after-rain
git remote add upstream https://github.com/minarry/harbor-after-rain.git
git config remote.pushDefault origin
git config user.name di
git config user.email 2195397+wandcs@users.noreply.github.com
node --version
npm --version
npm ci
npm test
npm run check
npm run build
npm start
```

打开 `http://127.0.0.1:4173`。`npm start` 前必须构建；离线构建为 `dist/offline/harbor-after-rain.html`，静态预览为 `npm run preview:offline`。操作与配置见[项目 README](../README.md#运行)。推送前在新电脑配置自己的 GitHub 登录，核实账号为 `wandcs`；克隆只会建立 `origin`，不会复制旧电脑的 `upstream`、作者和其他本地 Git 设置。

仓库的 `.gitattributes` 将 JS、MJS、Python、CSS、JSON、Markdown 和源码 HTML 固定为 LF，Prettier 也明确要求 LF；无需更改全局 `core.autocrlf`。历史离线发布 HTML 沿用原检出策略，不在本次修改范围内。配置机制见 [Git attributes 文档](https://git-scm.com/docs/gitattributes)。已有工作区如出现格式失败，先检查 `git ls-files --eol` 及编辑器换行设置；保留未提交改动，不用全仓格式化、删除锁文件或强制重置来掩盖问题。

## 4. O4 当时在验证什么

O1—O3 已实现紧凑协议、有界公共量化、确认基准差量和独立压缩块；O4 检查节省流量后，有效同步、CPU、真实操作和弱网质量是否一起达标。普通容量窗口通过不等于 O4 整体通过。

本节记录的是 2026-11-14—15 当时版本的证据，后续规则统一及当前构建不能直接沿用其全部性能结论。弱网比较曾用 protocol 2 的原始参考和 protocol 9 的候选，双方规则一致；多数网络诊断是 WSL Ubuntu-26.04 / Linux 6.18.33.2、Node 24.18.0 的短窗口，并非公网或真实双设备验收。同种子不能固定每次 TCP 分段、丢失位置、重传相位与调度。

原相对门槛是候选状态年龄 p95/p99 不高于参考加一个 60 Hz 同步周期（16.67 ms），受损和健康连接分别检查；浏览器健康页完整状态最大间隔线为 150 ms。整个调查没有放宽这些线，也没有用平均值、退出码或一次有利窗口覆盖失败。

## 5. 已做尝试、结果及采用情况

| 尝试 | 证据和结果 | 结论与决定 |
| --- | --- | --- |
| 编码与压缩选择 | 紧凑协议、量化、确认基准差量及有界 DEFLATE 块进入实现；正式容量窗口取得通过记录。LZ4 互操作已验证但带宽收益不足；逐小片 streaming inflate 曾使生成器约 10.6 Hz，属于无效负载；提高压缩等级未解决联合预算问题 | 保留成熟、简单且有界的实现。现行服务器 zlib level 6 / memLevel 4，浏览器 fflate 0.8.3，WebSocket PMD 关闭；旧“level 9”记录已勘误，不继续叠加机制。见[带宽记录](online-bandwidth-test-results.md) |
| 联合验收中的夹具边界 | 曾把达到 50 分的正常结算当作慢连接停滞，又机械要求心跳/时钟条件先触发的退出必须归因状态超时。这些检查失败均保留，随后按实际 leave/create/join 重建隔离片段的房间，并分别验证心跳、状态和时钟退出条件 | 修正测试前提和分类，保持生产结算、退出条件和质量线；不能为原夹具假设改产品。会话关闭后仍创建恢复定时器的真实缺陷则修复生产清理，用现有 O3-C1 回归验证。见[带宽记录](online-bandwidth-test-results.md) |
| W1 测量校准、W2 时钟/RTT 修正 | 校准实际丢包与完整状态年龄，区分输入 RTT 和显示 RTT，匹配 ping/pong。时钟误差明显减少，但三组丢包的真实尾部年龄没有改善 | 这些修正有正确性价值，已采用；不能把时钟估计变准当成真实弱网延迟改善。见[前两步记录](online-weak-network-test-results.md) |
| 分拆 TCP 重传、ACK 与旧快照积压 | 一轮 60/30 Hz 短断网中，链路恢复后仍等约 594/617 ms 才重传；首个完整快照再到旧状态排空约 15.8/49.9 ms，30 Hz 中约 43 ms 是 ACK 推进等待。丢包另见 0—45 ms 待发等待，与 ACK/拥塞恢复耦合 | 主等待并非应用解码或单纯旧快照字节量；不能把排队长度直接当作可节省延迟。见[归因记录](online-weak-network-attribution-results.md) |
| 通用发送窗口候选 | 未进入生产实现。它无法取消已经交给 TCP 的缺失前缀，也不能直接消除重传退避；上述 0—45 ms 尚未证明是窗口可取得的净收益 | 暂不做窗口。避免为不确定收益新增窗口/字节/年龄上限、基准所有权和重要消息进展等维护成本 |
| 30 Hz 短断网 RTO/ACK 三个对照 | 基线、服务器 RTO 下限 100 ms、客户端 ACK 请求 10 ms（实际 12 ms）各一窗。RTO 组追到新鲜状态慢 214.16 ms；ACK 等待少 28.03 ms，新输入真正执行却没有改善 | 停止继续调参，生产默认不变。更低 RTO 会碰到不同退避相位；浏览器页面也不能设置该 ACK socket 选项。局部 ACK 收益不足以产品化。见[TCP 对照](online-tcp-recovery-test-results.md) |
| 原 O4 退化与实际操作核查 | 60 Hz 短断网一轮真实年龄仍增加约 59—62 ms；丢包也有失败。浏览器两档新操作可恢复，但 30 Hz 健康页曾出现 162/186 ms，超过 150 ms 线 | 功能能恢复与质量达标分开记录。旧失败保留，不能认定为固定压缩开销或用能操作覆盖退化。见[退化核查](online-o4-regression-review.md) |
| 三个诊断窗口、修正恢复夹具 | 诊断将几毫秒统计读取、TCP 退避和浏览器入口等待分开。随后把 qdisc 统计移到断网中段，错过采样时优先恢复，不再恢复前同步读统计；修复验证通过，TCP 长等待仍在 | 采用小而可靠的夹具修正。它减少测量扰动，不能保证消除 TCP 相位差。见[三个诊断](online-three-diagnostics-results.md)、[夹具修正](online-fixture-cdp-control-results.md) |
| 修正夹具后的 O4 配对复核 | 丢包和短断网各参考/候选一次，共四窗，无追加重跑。丢包本轮相对门槛通过；60 Hz 短断网受损端 p95/p99 仍增加 113.52/114.48 ms。首消息入口晚 131.92 ms，首条应用工作均不足 1 ms；新输入执行仅晚 32.54 ms | O4 保持未通过。差额主要已发生在应用入口之前；ss 粗略相位相差约 134 ms 是 TCP 相位旁证，不能精确分配重传、发送排队和调度的全部责任，也不能把状态年龄增量直接当作操作延迟。见[四窗记录](online-o4-corrected-pair-results.md) |
| CDP 在线/离线最小对照 | 同一浏览器用例在线时健康页最大间隔 51.4 ms，CDP 离线时 193.5 ms；后者原生完整收齐间隔仍约 48 ms，原生收齐到 JS 最多等待约 512.5 ms，单条解码不足 1 ms | 证据收窄到与本环境 CDP 离线条件相关的浏览器交付延迟，具体 Chrome 内部原因未知。保留失败，不因此改生产解码、GPU/调度参数或质量线。见[CDP 对照](online-fixture-cdp-control-results.md) |
| Windows 浏览器连接 WSL 服务 | 仅新增在线/离线两窗：健康页最大间隔 40/136.5 ms，本轮通过 150 ms 线；离线原生收齐到 JS 仍最多等待约 489 ms | 服务、驱动、跨系统链路和负载同时变化，不能单独归功内核；旧 O4 四窗本来就在 Linux。新记录不覆盖旧 Windows 失败，也不关闭 O4。见[WSL 对照](online-wsl-browser-results.md) |

四窗之后还曾只读既有记录做离线拆分，没有重跑：候选“恢复到三个新鲜 tick”多约 140.74 ms，其中首消息入口前 131.92 ms、首条处理多 0.30 ms、首条应用后追赶多 8.52 ms。它与分布年龄的 113/114 ms 是不同指标，不能混加。ss 的粗略最近发送相位差约 132.60 ms，按恢复边界对齐约 129.70 ms，与首消息差相容；约 2.21 ms 的数值余差也不能直接命名为“调度耗时”。当时缺少该四窗的精确包级和逐次调度记录，ACK/RTO 状态也在变化，无法作充分因果分摊。两版健康端和模拟持续推进，不支持一次全局 132 ms 应用停顿，但不排除累积或单连接调度影响。首批之后累计应用工作只多约 3.23 ms，并与传输交错，不能重复相加。这也是最终没有贸然修改发送队列或调度的原因；本段保留该次本地分析的结论，续接无需原分析目录。

## 6. 最终决策与后续边界

用户已确定这是验证玩法的试验项目，现阶段先不做进一步即时性能优化。优先保证技术可靠、方案成熟、复杂度与实际玩家收益相称；不为解释少数短窗口而替换传输架构、累积特殊处理、扩大参数矩阵或反复重跑。

当前决定：

1. 保留已实现且验证过的编码、时钟与夹具修正；继续使用单进程权威服务和 WebSocket、现有同步档位与生产参数。发送窗口、TCP 生产调参及新传输方案均未进入。
2. O4 的 60 Hz 短断网相对退化保持未通过；浏览器 CDP 条件的环境影响也没有完全定因。没有证据证明一个简单可靠的生产修复能解决剩余问题，暂缓进一步优化比增加不确定机制更符合当前目标。
3. 此次不再要求迁移冻结源码和旧包，是收敛续接材料范围，不是删除失败结论、宣布验收通过或放宽门槛。日常开发先按当前产品需求和少量高覆盖测试推进。
4. 不因换电脑自动恢复 O4 实验或重跑历史矩阵。用户明确恢复该工作，或真实设备/目标网络出现影响可玩性的可复现问题时，先明确要解决的问题、力度与可解释的最小验证方案，再决定下一步。
5. 未来正式发布仍按发布约定准备当次完整产物、配套配置与回退能力；此次旧实验包不再是前置依赖，不撤销未来发布的运行与回退要求。

## 8. 换行修复的验收方式
