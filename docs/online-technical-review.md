# 《运输船：暮雨行动》联网技术评审意见

日期：2026-11-13。评审对象：[联网技术方案草案](online-technical-design.md)。产品依据：[联网产品设计](online-product-design.md)。

**评审结论：有条件通过。** 服务器权威、Node.js 单进程、内存房间和 WebSocket 适合当前玩法验证阶段；实施前应补齐多房间容量边界、同步数据结构、慢连接处置和命中姿态验证。优化优先减少传输内容与重复计算，按实测结果增加复杂度。

当前联网功能尚未实现。本文汇总方案与源码评审、公开工程资料及优化适用性判断；带宽数字属于估算，房间容量、弱网手感与优化收益仍需在目标服务器上验证。本文独立记录评审意见，不替代产品规则，也不表示技术草案已按这些意见修订。

修订跟进：本次评审的主要建议及后续讨论已纳入[技术方案修订草案](online-technical-design.md)。后续已确定状态同步仅设默认 60 Hz、低档 30 Hz 两档，模拟保持 60 Hz。下文保留原始评审上下文，其中 20/30 Hz 对照等旧候选以修订草案为准；文档修订不代表实现或性能验证已完成。

## 1. 保留的技术方向与产品边界

保留服务器统一计算角色、机器人、命中、比分和计时；客户端预测自身必要操作，通过快照插值显示其他角色。首版继续使用有限的枪械命中回溯，在线、离线复用必要模拟计算。

以下产品约定应作为实现和优化的边界：

- 一台云服务器，通过 IP 访问，面向小规模试玩；不预设商业部署规模。
- 房间容量沿用 4v4、5v5、8v8；一名真人即可开局，机器人补满空位。
- 没有房主，创建者离开后其他人继续游戏；允许对局中加入。
- 任何在场真人都可以暂停、恢复，首版不增加投票、次数或冷却限制。
- 断线按离场处理，再次加入按新玩家处理；不保留席位或恢复个人战绩。
- 保留两种玩法、现有枪战规则和可独立运行的离线单 HTML。

本地预测、插值和有限回溯直接影响移动目标射击与操作响应，属于射击可玩性的基础能力。其时间关系可参考 [Riot 的公开网络设计说明](https://www.riotgames.com/en/news/peeking-valorants-netcode)；具体频率、缓冲和窗口仍按本项目实验收敛。

## 2. 单进程多房间

### 2.1 状态独立，计算预算共享

每个房间持有独立的角色、机器人、比分、计时、暂停状态、输入队列和命中历史。服务器将连接绑定到房间及角色，广播只遍历该房间成员。A 房间暂停或结算，不应改变 B 房间的状态。

单进程内的所有房间共享 JavaScript 事件循环。一个房间计算过重会拖慢其他房间；进程崩溃或重启会结束全部房间。这一故障范围与当前内存房间、重启后重新加入的方向相容，首版接受这个限制。

60 Hz 对应约 16.7 ms 的步进周期。全部房间的模拟需要共同适应这个预算，并为消息处理、序列化、垃圾回收和调度留余量。增加定时器或使用 `async` 不会让同步模拟计算自动并行。[Node.js 官方说明](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)解释了长计算阻塞事件循环的影响。

### 2.2 按房间和机器人负载验证容量

一个真人创建 8v8 房间后，服务器仍要运行另外 15 个机器人。真人数较少并不意味着计算负载较低；多个各有一名真人的房间，可能比这些真人集中在一个房间更耗 CPU。

首版应配置最大活动房间数和总连接数，达到容量时提示服务器繁忙。上限根据目标服务器在最大房间人数、高机器人占比及高交火强度下的结果确定。先采用固定配置，不增加自动扩缩容或自适应接纳系统。

容量验证应同时记录每房间和全进程耗时，关注 p95、p99、最大值与调度落后，不能只看平均 CPU。创建房间时的地图、导航初始化也要测，避免新房间启动使已有对局突然卡顿。

同一地图的静态布局、碰撞定义和导航数据可在职责明确后复用；房间动态状态及查询临时缓冲应保持正确隔离。现有 [`World` 和 `NavGrid`](../src/physics.js) 包含查询标记和搜索工作数组，不能直接把完整实例当成只读数据共享。

## 3. 房间状态同步

### 3.1 按用途定义消息

客户端提交操作，服务器按固定步长推进真人与机器人，再向房间成员发送权威结果。联网客户端不重复运行整场机器人 AI。

| 信息 | 必要内容 | 发送方式 |
| --- | --- | --- |
| 大厅列表 | 房间号、模式、真人数、剩余时间、密码标志 | 进入列表时获取，之后低频刷新 |
| 加入初始化 | 规则标识、角色身份、阵营、当前完整状态及事件边界 | 加入成功时发送 |
| 房间动态快照 | 角色位置、速度、朝向、必要姿态，以及手雷、比分、据点 | 比较 20 Hz 与 30 Hz |
| 游戏事件 | 射击、伤害、死亡、角色更替、暂停、恢复、结算 | 发生后及时发送 |
| 本人校正状态 | 已处理或作废的输入边界，以及重放所需的自身状态 | 随快照只发给本人 |

完整快照应覆盖必要动态状态。禁止直接序列化整个游戏或角色对象；地图模型、材质、武器参数表、AI 寻路过程和个人画质设置不应反复传输。固定元数据在初始化或变化时处理，雨、抛壳、弹孔等表现尽量由客户端依据必要事件生成。

20/30 Hz 网络同步与 60 Hz 模拟、客户端渲染分别调度。成员获得同一模拟步的状态，但网络到达与显示时间各不相同；其他角色通过插值显示，本人通过预测响应操作。

### 3.2 共享公共快照，单独发送本人状态

房间公共状态尽量只构建和序列化一次，向成员复用同一份数据。输入确认和本人预测校正状态单独处理，避免为每名玩家重复编码全部角色。[Colyseus 的优化文档](https://docs.colyseus.io/state/optimization)也区分了全房共享编码与按客户端过滤编码的成本。

快照应明确房间标识、模拟步、网络时间、对局时间、流程状态、角色身份与生命编号、事件边界和输入确认边界。公共表现数据与本人校正数据的字段应分别列清。

本人校正数据必须足以恢复预测起点。现有 [`WeaponState`](../src/weapons.js) 和 [`Actor`](../src/actor.js) 包含射击冷却、换弹时间、弹药、散布累积、射击计数、后坐力及其他相关状态；只恢复位置和血量可能使重放后的射速、弹药或弹道继续偏离。

### 3.3 成员变化与事件边界

保留草案中“加入快照与后续事件处于同一状态边界”的设计。最终检查容量、分队、移除机器人和放入真人应形成一次完整状态变更；跨异步准备过程后，要按生效时的房间和连接状态重新校验。

角色替换生成新身份，复活生成新生命编号。旧输入、旧事件和插值不得串到新角色或新生命。暂停恢复时清空旧输入并更新阶段边界；暂停期间继续处理连接、成员变化和存活检测。

服务器结算只执行一次，房间清理不依赖所有客户端确认。事件与快照中的最终状态应有明确的去重和应用规则，避免重复播放、扣弹或计分。

## 4. 消息体积与带宽

### 4.1 已有估算的含义

讨论中按代表性字段构造的 JSON 样例，8 个角色约 1.65 KB，16 个角色约 3.11 KB。样例包含身份、生命编号、阵营、位置、速度、角度、姿态、血量和部分武器状态，未包含完整本人校正状态、手雷和事件，因此不能作为最终包体或上限。

容量计算统一采用以下明确假设：每次快照 4,000 字节，16 名真人接收；KB、MB 按十进制计。实际测量应使用编码后字节数，而非字符串长度。

| 同步频率 | 单玩家下行 | 单满员房间服务端出网 | 三个满员房间服务端出网 |
| --- | --- | --- | --- |
| 20 Hz | 80 KB/s，0.64 Mbps | 10.24 Mbps | 30.72 Mbps |
| 30 Hz | 120 KB/s，0.96 Mbps | 15.36 Mbps | 46.08 Mbps |

计算关系：`服务端出网（bit/s）= 每次快照字节数 × 每秒次数 × 真人接收人数 × 8`，除以 1,000,000 得到 Mbps。多房间按实际接收人数求和，机器人不占客户端下行连接。

上表只计算假设中的状态快照，尚未计入其他消息、协议开销、重传和页面下载。购买云服务器时需同时核对出网带宽；在该假设下，5 Mbps 出口无法承载一个满员房间。

### 4.2 简单编码优化应提前评估

保留 JSON 作为最小样例的可读基线，同时尽早比较简单二进制编码。优先使用数字编号、有限精度数值和组合状态标志，保持必要动态状态完整，不先引入复杂差量算法。

浏览器射击游戏 Suroi 的源码使用有限范围整数编码位置，并组合编码输入开关，可参考其[位置序列化](https://github.com/HasangerGames/suroi/blob/master/common/src/utils/suroiByteStream.ts)和[输入消息](https://github.com/HasangerGames/suroi/blob/master/common/src/packets/inputPacket.ts)。Suroi 是二维射击游戏，这些资料支持编码方法，不直接决定本项目的三维命中精度和同步参数。

作为收益量级对照，如果相同必要信息从 4,000 字节减至 1,500 字节，16 名真人、20 Hz 的快照出网将从 10.24 Mbps 降至 3.84 Mbps。1,500 字节仅是对照假设，尚未证明能容纳最终字段。

量化先作用于网络表示。公共表现与本人预测校正可以有不同精度要求；必须验证头部命中、掩体边缘、楼梯和高台处的误差，避免为缩小消息改变权威模拟规则。[Gaffer 的快照压缩文章](https://gafferongames.com/post/snapshot_compression/)说明了按范围与实验精度编码位置、速度和角度的方法。

## 5. 慢连接和积压

草案已正确区分应用层待发送快照与进入 TCP 的数据，实施时应补齐阈值、持续时间和处置：

- 每个连接独立观察发送积压；可结合 [`ws.bufferedAmount`](https://github.com/websockets/ws/blob/master/doc/ws.md#websocketbufferedamount) 和积压持续时间判断。
- 积压较大时停止追加旧位置快照，保留尚未发送的最新完整状态。
- 重要事件队列同样有界；持续无法恢复的连接按断线规则处理并补机器人。
- 房间推进和广播不等待所有客户端确认；慢连接独立处置。
- 客户端上行也要有界，归零输入和过期策略防止恢复后集中执行旧移动或射击。

已经进入 TCP 的旧数据无法撤回，后续结算或暂停消息也无法越过这些字节。快照合并有助于减少积压，但不能消除 WebSocket 的传输层阻塞；这一边界来自其基于 TCP 的协议设计。[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)

首版同时限制消息大小、字段范围、消息频率和输入队列长度。服务器根据连接身份确定可操作角色，并检查有限数值、合法动作和模拟时间预算。这些措施用于保护对局稳定性，保持小范围实现，不扩展为专门的反作弊或防护平台。

## 6. 命中姿态和预测是主要实现风险

### 6.1 提取影响命中的姿态计算

现有 [`Actor`](../src/actor.js) 创建时直接创建 `Soldier` 并加入渲染场景；[`Soldier.hitTest()`](../src/character.js) 使用头、胸、腹、手臂和腿部骨骼矩阵。骨骼还受步态、下蹲过渡、后坐力和受击动作影响，步态具有随机初始相位。

因此，只同步位置、朝向和下蹲开关，不能保证玩家看到的身体与服务器判定一致。应提取影响命中的必要姿态计算，明确重建姿态所需状态。服务器只保留计算和有界历史，不创建材质、网格和声音；网络不默认广播完整骨骼矩阵。

现有 [`Player.shotOrigin()` 与镜头更新](../src/player.js) 也有耦合。拆分时应核对射击起点、后坐力和受击偏转，避免提取过程改变实际弹道。未经验证，不用另一套粗略命中盒或射击姿态替代现有规则。

### 6.2 保持预测、插值和回溯的一致时间关系

沿用草案的 60 Hz 操作帧、约两个快照间隔的显示缓冲和可调的 200 ms 回溯上限作为实验初值，结合实际交火结果共同调整。

输入编号应对应明确的模拟消费边界；已确认边界代表执行或明确作废，不能仅表示收到消息。迟到输入不能让角色多推进时间，一次性操作只消费一次。随机散布和后坐力应稳定关联生命、武器与射击编号，重放仅重算状态，声音和特效去重。

命中回溯查询玩家开枪时实际看到的目标历史，结合连接时间采样限制窗口；旧生命和暂停阶段不能跨边界命中。插值缓冲与传输延迟共同影响所需历史长度，200 ms 回溯上限不等于承诺支持 200 ms RTT。

姿态降频应在正确实现和热点测量后评估。Riot 曾公开介绍降低服务器动画计算频率、查询历史时插值的优化；其具体倍率建立在当时 128 Hz 模拟及自身验证上，不能直接套用于我们的 60 Hz。[公开案例](https://www.riotgames.com/en/news/valorants-128-tick-servers)

## 7. 常用优化的适用性与进入条件

| 优化方式 | 对本项目的判断 | 实施范围或进入条件 |
| --- | --- | --- |
| 模拟、同步和渲染频率分开 | 首版采用 | 保留 60 Hz 模拟，比较 20/30 Hz 同步；不为省带宽直接降低全部游戏逻辑频率 |
| 固定、连续和离散信息分开同步 | 首版采用 | 固定数据初始化，连续状态定期同步，事件及时通知；加入仍获取完整当前状态 |
| 公共快照只编码一次 | 首版采用 | 公共数据共享，本人确认和校正状态单独处理 |
| 数值量化、简单二进制 | 优先小样例评估 | 比较同一份必要状态的字节量、编码耗时和量化误差，再确定首版格式 |
| AI 决策降频、错峰 | 保留已有机制 | 现有思考间隔约 0.13～0.19 秒并有随机错峰；测量寻路尖峰后再调整 |
| 空间查询、命中粗检 | 保留已有机制 | 现有地图网格与人物粗检继续复用；最多 16 人时不另建通用空间系统 |
| 静态地图数据复用 | 提取时按职责处理 | 复用静态定义和可证明只读的数据；检查创建尖峰，隔离动态状态与工作缓冲 |
| 临时对象和缓冲复用 | 按热点补充 | 测到分配和垃圾回收尖峰后，针对命中查询、历史和编码等热点处理 |
| 差量同步、脏标记 | 后置 | 紧凑完整快照仍超出带宽预算，且测得变化稀疏、收益明确时进入 |
| 兴趣区域和相关性裁剪 | 暂缓 | 地图或人数扩大、无关实体占比明显后再评估；同时覆盖声音、雷达和远距离射击 |
| 命中姿态降频 | 按热点评估 | 姿态正确性已验证、计算确为热点，并通过动作和回溯误差对照 |
| 输入批量发送或减少重复输入 | 后置 | 消息频率成本明显时评估；保留操作时间、边沿和输入新鲜度，测量新增等待 |
| WebSocket 通用压缩 | 默认关闭 | 精简字段和紧凑编码后仍有带宽瓶颈，且 CPU、内存与延迟对照显示净收益时开启 |
| WebTransport 或 WebRTC DataChannel | 弱网证据触发 | 控制消息量和调度后，目标网络仍持续出现影响玩法的传输积压，再比较部署与设备成本 |
| 少量固定 worker 或进程 | CPU 容量证据触发 | 多房间持续超预算，热点优化收益不足且机器有空闲核心时评估；整房间归属一个执行单元 |

差量同步的收益取决于实际变化比例。昵称、规则等低频信息避免重复发送很划算；交火中多数角色的位置和角度持续变化，不能预设压缩倍数。WebSocket 的有序可靠传输可以简化基线管理，但应用层跳过或合并依赖先前状态的补丁时，仍需重建正确基线或发送完整快照。[原理说明](https://gafferongames.com/post/snapshot_compression/)

相关性裁剪适合大量实体中只有少量会影响当前玩家的场景。[Epic 文档](https://dev.epicgames.com/documentation/unreal-engine/actor-relevancy-in-unreal-engine)说明了这一机制。对当前紧凑地图和最多 16 人的推断是：角色可能迅速进入交火、声音或雷达范围，筛选及进入离开处理的成本未必值得；首版同步房间全部角色更容易验证。

压缩和传输替换都有额外成本：[`ws` 官方文档](https://github.com/websockets/ws#websocket-compression)提示通用压缩的性能与内存开销；[WebTransport 文档](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport)要求安全上下文，需要连同当前 HTTP IP 访问和目标设备一起评估。[Node.js worker 文档](https://nodejs.org/api/worker_threads.html)支持用并行执行分担 CPU 计算，但实际收益仍取决于房间负载和消息传递成本。

现阶段继续延后数据库、Redis、消息队列、房间迁移、多地域部署、复杂可见性系统和通用同步框架。保持房间职责独立，为后续按证据拆分执行单元提供基础即可。也不改为玩家托管或要求所有客户端确定性运行整场对局，以免扩大创建者离开、设备差异和状态一致性的处理范围。

## 8. 实施顺序与验收证据

### 8.1 先验证一条真实的联网交火链路

建议将技术草案中“先提取两种完整玩法，再做联网样例”的顺序调整为更窄的实现链路：

1. 提取真实地图移动、一把枪、必要命中姿态和相关状态，离线入口同时使用提取后的实现。
2. 两台真实设备进入同一房间并保留机器人，完成输入确认、预测重放、插值和有限回溯。
3. 在延迟、抖动与真实丢包环境中验证移动目标、掩体交火和暂停阶段边界。
4. 对同一份完整必要状态比较 JSON、简单二进制和 20/30 Hz 同步，收敛格式与频率。
5. 补齐全部武器、两种玩法和完整房间流程，测试跨设备、多房间及资源释放，确定接纳上限。

这只是降低早期验证成本的实施顺序；最终仍需满足两种玩法、人数选项、机器人补位、平等暂停和离线交付要求。

### 8.2 最小验证矩阵

| 场景 | 必须取得的证据 |
| --- | --- |
| 单房间 8/10/16 人、高交火强度 | 全部必要状态和事件的真实字节量，模拟与编码耗时，完整命中历史的开销 |
| 多房间各一名真人、其余机器人 | 总计算预算、AI 与寻路尖峰、调度落后；据此确定固定容量配置 |
| 已有对局运行时创建新房间 | 初始化耗时及对其他房间的影响，静态数据复用是否正确 |
| 单个慢客户端或短时断网 | 队列有界，不集中补执行旧操作；其他客户端继续正常游戏 |
| 同时加入最后空位、退出、复活、结算 | 无超员、重复替换、旧生命操作和重复结算；输入与事件边界可追溯 |
| 多房间暂停、恢复和关闭 | 房间之间无状态串扰，暂停仍处理连接，最后真人离开后资源释放 |
| 静止与运动目标、头胸四肢、下蹲跳跃、掩体边缘 | 可见姿态、服务器判定与回溯结果一致；量化和姿态降频误差有对照 |
| RTT 0/50/100/150 ms，并增加抖动、丢包 | 实际交火观察、积压和校正幅度；丢包测试包含 TCP 重传影响 |
| 电脑与手机、30 FPS 与较高帧率 | 移动和射速一致，操作边沿有效，后台或转屏只清除本人的输入 |
| 反复开关房间及离线独立运行 | 连接、定时任务、历史与临时状态释放；断网单 HTML 保留完整玩法和操作 |

每轮记录服务器配置、设备、网络条件、构建版本、编码格式和频率。至少测量每类消息字节量、总出网、发送积压及持续时间、RTT、快照间隔、预测校正幅度、每房间与全进程步进耗时、事件循环延迟、内存和垃圾回收尖峰。

最大房间数、积压阈值、输入新鲜度和可接受校正幅度在样例中收敛，随后写入集中配置及验收标准。连接成功、同机多标签页、画面截图或程序化快进，均不能单独证明真实交火质量和服务器容量。
