# S5 本地软件与实验记录

日期：2026-11-14。依据：[测试方案](s5-test-plan.md)、[技术方案](online-technical-design.md#21-多房间隔离与总预算)及[研发约定](development-guide.md#8-测试验收与证据)。用户要求继续 S5，实机仍暂缓；目标服务器尚未提供。本轮完成本地工具、软件修复及实验，**S5 目标机与真实体验验收未完成，未进入 S6**。

## 软件改动与用例

新增一条永久服务器用例 S5-R1：实际触发全进程连接/房间上限、验证拒绝原因、已有房间推进和释放后接纳，并检查导航工作缓冲隔离。支持按编号独立选择，自建服务并清理。

加强原 S4-R2 与 app 生命周期用例，首轮真实复现两项缺陷：

- 同一连接进入相同规模的新房间时，旧 rosterVersion 与新房间碰巧相同，服务器漏发成员表；实际客户端会因 ROSTER_MISSING 退出。加入时重置成员版本，确保首次完整成员信息。
- 离场后输入队列和已发送快照引用仍留在列表连接上；离场边界清除队列、沿用输入及引用。

首轮 `reuse-red` 为 14 通过、2 失败，修复后服务器组 17 项通过；累计 **198 项通过，0 失败、0 跳过**。新增永久用例只有 1 条，实验配置、回收轮次和浏览器运行分开计数。

## 容量实验与开发默认值

实际 createApp、房间、AI、输入、快照和传输在独立 Node 进程中运行。另一进程使用真实 OnlineSession 的时钟、输入帧及显示采样产生负载；不运行渲染或预测物理。两进程仍共用本机硬件，不能代表云端或公网。

硬件：AMD Ryzen 7 9700X，16 个逻辑处理器，约 30.9 GiB 内存；Windows 10.0.26300 x64，Node.js 24.18.0、npm 11.18.0。每级预热 2 秒、采样 6 秒。工程筛选线预先确定：全体房间单步工作 p95≤12.5 ms、p99≤16.67 ms，实际步进≥59 Hz，事件循环 p99≤33.33 ms；生成器不足单独标记。

E1 正式探索为六个负载/档位配置、16 个级别，另做两档开发默认候选的混合确认点，共 **18 个测量级别：15 个在预算内、3 个超预算**。实验成功完成不等于每个压力级别都合格。单房间工具初测另存 `capacity-smoke`，不叠加进正式数量。

| 负载点 | 60 Hz：单步 p95 / 事件循环 p99，ms | 30 Hz：单步 p95 / 事件循环 p99，ms | 本轮筛选结果 |
| --- | --- | --- | --- |
| 8 房，每房 1 真人+15 机器人 | 7.17 / 26.53 | 6.16 / 26.15 | 两档在预算内；更高房间数未测 |
| 2 房，每房 16 真人 | 6.28 / 25.97 | 5.18 / 24.74 | 两档在预算内 |
| 4 房，每房 16 真人 | 10.59 / 36.08 | 8.49 / 27.21 | 60 Hz 超预算，30 Hz 在预算内 |
| 8 房，每房 8 真人+8 机器人 | 16.78 / 40.76 | 14.46 / 33.29 | 两档超预算；房间/连接上限不能分别推定组合可用 |
| 2 房，每房 8 真人+8 机器人 | 5.64 / 25.20 | 4.20 / 20.02 | 两档在预算内，作为保守开发候选的补充证据 |

因此将**本地开发默认**从 8 房/64 连接收紧为 **2 房/32 连接**，仍允许显式配置 MAX_ROOMS=1–32、MAX_CONNECTIONS=1–256。没有减少玩法人数、降低 60 Hz 模拟、引入自动降档或改变队列/同步阈值。默认值属于本机保守基线，**不是目标服务器最终容量或部署保证**。

负载驱动为探索显式设置 8 房/64 连接上限；候选确认点限制实际负载为 2 房。生产默认本身由配置断言、上限用例及最终浏览器复验检查。没有将实验驱动上限误认为生产默认。

出网需单独约束：单个满员 8v8 房间，本轮 TCP socket 出站字节折算约 **108.0 Mbps（60 Hz）/58.0 Mbps（30 Hz）**；两个满员房间约 217.2/115.8 Mbps。包含 WebSocket 数据，不包含 IP/链路头与重传，不能当作公网线速。当前仍使用 JSON，目标机带宽未知，未据此新增压缩、差量或付费资源。

记录包含每房间与全局步进、定时落后、事件循环、进程 CPU、GC、双方字节、队列、创建尖峰和内存。正式级别的创建处理峰值约 54.1 ms，RSS 50 ms 采样峰值约 290.6 MiB；创建瞬态与稳定窗口分开，不用预热掩盖尖峰，也不把采样峰值称为精确的进程高水位。CPU 百分比为进程计时，100%约对应一核；生成器自身 CPU/延迟/实际输入数单列。

## 回收与回归

E2 两档各 24 轮，按同一规模连续两轮后再切换，覆盖 4v4/5v5/8v8、双玩法、退出、断线、结算及同一连接再入场。实际 OnlineSession 也完成了成员版本相同的新房间链路。

每六轮强制 GC 检查一次：每档共观察 96 个旧房间/对局/世界/导航对象的弱引用，检查点残留均为 0；第 12/18/24 轮堆样本跨度约 36.0 KiB（60 Hz）、32.7 KiB（30 Hz），低于预设 8 MiB 筛选量；ArrayBuffer 样本均为 226106 字节。清理后房间/连接/队列为 0，监听关闭，只有测量进程管道仍在。CPU 计时窗口未强制 GC；回收检查的强制 GC 次数单列。短样本不能证明长期无泄漏。

| 验证 | 本轮结果 | 证据根目录内位置 |
| --- | --- | --- |

在仓库根目录，Node.js 24.x / npm 11.x，先按锁文件安装并构建：

```sh
npm ci
npm run build
npm test
npm run check
node scripts/run-tests.mjs --case=S5-R1 --layer=server
node scripts/s5/run.mjs --case=S5-E1 --hz=60 --load=bots --rooms=2 --out=artifacts/online-s5/new-capacity
node scripts/s5/run.mjs --case=S5-E1 --load=mixed --rooms=2 --out=artifacts/online-s5/new-combination
node scripts/s5/run.mjs --case=S5-E2 --hz=30 --out=artifacts/online-s5/new-resources
```

`npm run test:s5` 执行六个探索配置和两档回收；`test:s5:capacity` / `test:s5:resources` 可分开运行。每配置有 120 秒守卫；请求与握手有超时，测量明细有数量上限，finally 清理。工具只创建自己的 loopback 临时服务，不需要已有服务、浏览器、WSL 或管理员；Windows 本地网络仍按仓库约定使用桌面身份。使用新输出目录，避免覆盖旧报告。目标机可运行相同 Node 工具，但仍需补真实 IP 访问、外部带宽与设备体验；同机生成器可能竞争目标机资源，不能把生成器不足当作服务器上限。
