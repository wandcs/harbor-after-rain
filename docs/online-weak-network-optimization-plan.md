# 弱网问题审查与优化方案

日期：2026-11-15。用户已确认并执行测量校准、两端时钟/RTT前两步，测试设计与实际结果见[测试设计](online-weak-network-test-plan.md)、[执行记录](online-weak-network-test-results.md)。发送窗口及后续路线仍有条件、未执行；现行通过线未改变，O4相对弱网指标仍待验。第2、4节保留方案形成时的证据和代码问题，不作为修复后行为描述。依据：[既有实现与结果](online-bandwidth-test-results.md)、[现行测试门槛](online-bandwidth-test-plan.md)及本轮网上调研。

后续按用户安排复用丢包/短断网作了[TCP归因](online-weak-network-attribution-results.md)：主要等待为重传退避；丢包中仍有0—45ms发送等待，但尚未证明窗口净收益，暂不进入通用发送窗口实现。原O4门槛保持，压缩等级另补勘误。

用户随后确认现阶段不做发送窗口。针对重传与ACK等待的[后续候选方案](online-tcp-recovery-optimization-plan.md)已完成调研：建议先研究服务器单连接RTO下限与接收端ACK上限的隔离对照，尚未编码、设置参数或执行；浏览器权限与目标机条件分别标明，不能把实验夹具能力当产品能力。

## 1. 目标与边界

在单房最多10真人，或最多两房合计10真人以内，减少弱网停顿、恢复后的操作等待和时钟误判；保留机器人补位、服务器权威、60 Hz模拟/输入、60/30 Hz状态同步。保证范围包含两房各1真人、共30机器人的AI上界。

先解决可证实的问题，不为一个分位数叠加机制。当前WebSocket、完整本人校正、公共基准确认与两份缓存继续保留。回溯225/250 ms、未来输入30步、预测队列128项、6秒新鲜度、8个未完成时钟请求和有界恢复不因本方案自动放宽。未完成的弱网指标仍待验，不能用新方案追认旧结果通过。

## 2. 现在的问题是什么

| 问题 | 已有证据 | 目前能下的结论 |
| --- | --- | --- |
| 60 Hz、0.9秒短断网 | 精确成对复测：原始年龄p95/p99为1085.04/1398.51 ms，候选1107.10/1434.28 ms，增加22.06/35.76 ms，超过16.67 ms相对线 | 差额仍存在，尚不能归因于压缩、发送排队或具体TCP恢复算法 |
| 60 Hz、1%丢包 | 首次相对未通过；成对复测候选106.13/167.24 ms，原始109.96/168.25 ms，本轮通过 | 结果有波动，不能挑一次成功判整体通过 |
| 时钟估计影响年龄 | 首次丢包按同tick核心步进到接收估算，原始/候选p95约135.27/130.80 ms，与SDK估计的94.10/131.92 ms不同 | 估计误差必须与实际交付延迟分开；核心步进时间只是诊断代理，不能冒充精确快照时间 |
| 恢复后的实际等待 | 从已记录tc恢复时刻，到连续3个同tick诊断年龄≤50 ms的状态，60 Hz原始/候选约568/606 ms，30 Hz约644/669 ms | 除0.9秒物理断网外，恢复尾部值得定位；这些是既有日志推导，尚非新验收结果 |

成对复测中，候选60 Hz短断网最长接收间隔约1518 ms，显示采样held为90/480，原始为1481 ms、87/480。`held`只表示采样没有两个插值端点，不等于每次都是可见卡顿。当前记录没有显示应用发送字节积压，候选事件循环监测最大约13.5 ms；它们不支持直接认定编码CPU是主瓶颈，也不能排除内核TCP队列。

现有8秒窗口约480/240个快照，p99只由尾部约5/3个观测决定；同一内核随机种子不代表两种报文布局经历了相同的逐包丢失。每包分位数还会受到重传后集中交付影响，不能独自描述屏幕停顿时间。

本轮只读分析产物：[既有数据摘要](../artifacts/online-bandwidth/20261115/weak-network-proposal/existing-evidence.json)。

## 3. 网上常见方法及适用性

| 方法 | 资料中的处理思路 | 对我们的判断 |
| --- | --- | --- |
| 稳健时钟估计 | 保留有限样本、优先低延迟样本、过滤异常、使校正平稳 | 优先。当前每次回复直接覆盖估计；借鉴方法，不引入完整NTP服务 |
| 发送背压与新状态优先 | 停顿时限制在途更新，待确认后发当前状态 | 有条件适用。不能撤回已经交给TCP的字节；不直接照搬固定3包窗口 |
| 插值缓冲/有界自适应 | 用少量显示延迟换取抖动容忍 | 可以改善显示，不能减少TCP重传等待或接收年龄；还受本项目回溯合同限制 |
| 接收后合并陈旧更新 | 避免恢复时逐包重放产生CPU尖峰 | 仅在实测客户端重放成为瓶颈时考虑；必须维护基准、事件和配对边界 |
| 不可靠状态传输 | 允许旧快照丢失，新快照继续到达 | WebTransport datagrams或WebRTC部分可靠通道是后续路线，当前不迁移 |

NTP规范用有限时钟样本并按延迟筛选；双向时延不对称仍会造成估计误差，滤波不能还原不可观测的单向时延。[RFC 5905 §10](https://www.rfc-editor.org/rfc/rfc5905.html#section-10)

GameDev.net的2017年讨论提出限制未得到反馈的更新数量，避免TCP停顿时继续积累；这是设计线索，不是本项目的窗口参数。[原讨论](https://gamedev.net/forums/topic/686253-websocket-based-realtime-multiplayer-game-client-and-server-communication/)

Gaffer的快照插值文章说明缓冲通过增加显示延迟改善抖动，其丢包示例以可跳过旧快照的UDP为背景；不能把该参数直接用于本项目的可靠有序流。[原文](https://gafferongames.com/post/snapshot_interpolation/)

TCP提供可靠、有序字节流；具体损失恢复可能涉及RACK/TLP等算法，不能只用“三次重复ACK”解释今天的所有实现。[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)、[RFC 8985](https://www.rfc-editor.org/rfc/rfc8985.html)

## 4. 对照代码发现的改进点

### 4.1 客户端时钟与RTT用途耦合

[OnlineSession](../src/net/session.js)收到clock后，以最后一份回复直接设置`rttMs`和`offsetMs`。同一个RTT同时进入输入目标步提前量、远端采样时间和延迟显示；`serverNow()`又影响输入时间、新鲜度和倒计时。一次重传或排队后的回复，可能同时扰动这些消费者。

建议先采用有限窗口、样本有效期与异常筛选，分别维护原始RTT、时钟偏移估计、输入调度余量和显示时间线。低RTT样本适合减少偏移估计的排队污染；输入提前量不能盲用最小RTT，否则持续增加的真实延迟会使输入长期迟到。显示时间线单独平滑，不能靠冻结逻辑时间掩盖陈旧状态。

优先使用现有报文字段验证收益。仅当测得服务器处理/应用排队不可忽略时，再考虑四时间戳；四时间戳也不能消除路径不对称，排队前生成的发送戳不等于实际写出时刻。

### 4.2 服务器pong没有与发出的ping对应

[server/app.js](../server/app.js)每秒更新`lastPingMs`，每个pong都用当前时间减该值。旧pong跨过下一次ping到达时，RTT可能被低估；该RTT还参与[历史回溯的连接窗口](../server/sync/history.js)判断。

建议ping携带小型序号，按匹配记录计算RTT，忽略重复/未知回复，待确认记录按现有超时有界清理。利用标准ping/pong负载回显，不增加游戏输入包或独立连接；保留原心跳退出规则。修复后检查合法显示引用的回溯与回退原因。

### 4.3 内存上限不等于低延迟发送上限

[Outbox](../server/transport/outbox.js)已能替换尚未发送的快照，但直到`bufferedAmount > 256 KiB`才停止追加。约100 KB/s流量下，256 KiB与数秒数据相当；此计算只解释内存门槛的尺度，不代表测得了这些积压。`bufferedAmount=0`不证明TCP内核没有未确认数据；`onSent`也不是客户端已解码确认。

若抓包/队列观测证明这是恢复尾部的重要来源，再增加按连接的解码进度反馈和发送窗口，见第6节。仅调小256 KiB不能覆盖隐藏在内核的排队。

### 4.4 生命周期与显示也要审查

陈旧检查目前在`frame()`内；产品的`simulate()`在暂停等状态会早退，弱网驱动又在角色死亡时跳过frame。需要统一会话的新鲜度检查入口，区别合法暂停与断网，不让检查是否执行取决于是否射击或存活。后台定时器会受调度限制，恢复前台时应立即按单调时间检查，而非承诺后台精确毫秒触发。

[SnapshotBuffer](../src/net/snapshot-buffer.js)会跨时间很长但生命周期相同的端点插值，`sample()`还直接使用最后RTT。若稳定时钟后仍有恢复期倒退/长距离追赶，再设计有限的显示重建边界；不伪造显示引用或额外修改远端骨骼。

本地安装的`ws`在`setSocket()`已调用`setNoDelay()`，所以“关闭Nagle”不作为新增优化。当前也没有证据要求增加压缩等级、扩大预测历史或盲目合并所有收到的快照。

## 5. 第一阶段：把测量与归因补齐

先加强S3-E2观测，不增加产品行为和永久用例：

1. 同时记录应用可观测的消息回调入口、解码结束、状态提交、预测校正结束。当前年龄统计在reconcile之后，不是纯网络到达时间。
2. 同进程用共享单调时钟直接核对`now - snapshot.nowMs`，与SDK估计年龄、偏移误差分列。跨进程校准只在同一内核、确认共用单调时间域时使用统一单调日志；不能直接相减两个进程各自的`performance.now()`。
3. 分别记录正常、断网中、链路恢复后三段。恢复指标从tc实际恢复完成时刻，到连续3个不同常规tick的完整配对状态回到对应正常年龄范围；另观察新输入是否真正被权威执行，不能只看收到或作废的ACK。
4. 显示采样记录持帧持续时间、目标时间是否倒退、校正幅度；逐包年龄与按时间采样的新鲜度同时保留。无渲染驱动不冒充真实体验验收。
5. 记录实际TCP恢复/未确认字节、包化、MTU、offload和队列位置。只在隔离命名空间采集必要TCP元数据/抓包，不修改宿主网络或引入产品诊断服务。

常规运行tick与生命周期额外发布分列，恢复后的集中交付不冒充均匀同步；“收到”“完整解码”“原子应用”“画面采样”分别计数，不通过丢掉不利样本改善分位数。

现有loopback netem仍可验证输入失效、去重、缓存和清理；其TCP性能结论需少量独立校准。iproute2文档明确提醒TSQ会影响TCP实验，建议在接收端入口施加netem。因此校准优先使用两个隔离网络命名空间和veth，在接收方向注入并固定MTU/核对offload；不要把loopback的一个skb直接当作公网一个MTU报文。[上游netem说明](https://github.com/iproute2/iproute2/blob/main/man/man8/tc-netem.8)

先只校准60 Hz丢包和0.9秒短断网两个失败/不稳定点；确认正常无故障基线可比。其他配置按影响复用。若数据不支持排队或客户端CPU占主要差额，停止对应优化分支，不能为了保留方案制造新机制。

执行时能力探测已证明同一临时命名空间内的接收侧IFB可完成MTU/offload校准，且可复用同进程共享单调时钟真值，因此采用该路径代替额外双进程/veth框架。原loopback作对照，拓扑不混用；实际包化/重传由ss、内核计数与tc记录留证，未进行包级抓包，不宣称公网等效。

## 6. 第二阶段：优先时钟，按证据进入发送优化

**先做两端时钟/RTT修正。** 客户端有限样本筛选、用途分离，服务器ping/pong精确匹配；保持既有频率和全部上限。用孤立尖峰、持续RTT上升、迟到回复及生命周期边界验证，不能通过“永远选择旧的最低RTT”取得漂亮数字。若这一步已解决真实体验与已确认验收目标，停止增加机制。

**发送窗口是有条件的下一步。** 只有测量证明持续向停顿连接投入可替代旧状态，显著延长恢复时，才进入：

- 使用独立的最高成功提交`snapshotAck`，不混用输入执行`ackSeq`、实际显示引用或稀疏的基准`baseAck`。优先搭现有输入/clock发送；无输入但仍接收时，需要有界的进度反馈，不能等同于正常数据停止。
- 窗口按RTT、反馈周期、抖动余量和同步周期估算，并同时限制数量、字节和年龄。不用固定3包：150 ms RTT、60 Hz本来就约有9个周期的数据在往返中，反馈与余量还未计入。
- 暂停向下游追加可替代快照时，核心照常60 Hz推进，历史照常维护，只保留当前待发快照。恢复时发送当前完整配对状态，必要时全量；不能冲刷一串旧状态或额外补执行旧射击。
- 基准确认、在途缓冲所有权、阶段/成员/生命边界保持，普通拥塞不能耗尽缺基准恢复的两次预算。必要的显示重建与普通周期全量区分，避免每次全量都清空画面缓冲。
- 重要控制与结算有界有序，不能因窗口停止而死锁；反馈也必须有独立进展路径。已交给TCP的旧字节仍不能取消。
- 限制发送也可能改变TCP损失恢复时序；必须观察是否减少了反馈、导致恢复更慢。正常有效同步率下降，或弱网真实恢复变差，就撤掉该候选。

不预先写死窗口、反馈频率或新软阈值。参数只能由第一阶段实测和已确认体验预算登记，原256 KiB硬上限及2秒积压退出不扩大。

## 7. 暂不进入的路线

| 路线 | 暂缓理由与重新进入条件 |
| --- | --- |
| 一律增大插值缓冲 | 增加显示延迟，不能改善接收年龄；150 ms RTT下回溯参考已接近225 ms线。若剩余问题只是抖动，再在现有回溯范围内讨论有界自适应 |
| 接收侧批量合并 | 可能节省重放CPU，但当前尚无此瓶颈证据。若进入，必须依序重建所有必要基准并保留控制/生命周期事实，不能靠少应用状态刷指标 |
| 调高压缩、攒帧、降低档位、放大队列 | 不针对已证实差额，可能把带宽成本转成CPU或额外延迟，且60/30 Hz是现有合同 |
| 应用重发、FEC、填充包、盲目切小TCP包 | 不能直接跨越可靠字节流的前序缺口；增加流量和实现成本，缺乏本项目的收益证据 |
| 立即换WebTransport/WebRTC或双WebSocket | 新部署、浏览器能力、连接与清理成本明显；目前10真人容量已通过，先验证小改动是否足够 |

若TCP前序数据恢复成为已确认的主要瓶颈，且无法满足确认后的体验目标，再单独评估“可靠控制＋可过期的状态数据”。WebTransport提供可靠/不可靠能力，WebRTC数据通道可配置乱序与重传/生存时间；只把同一快照流换成另一个可靠有序流不能宣称消除等待。[WebTransport规范](https://www.w3.org/TR/webtransport/)、[WebRTC规范](https://www.w3.org/TR/webrtc/)

迁移还要处理数据报最大尺寸、可能的分片与期限、乱序/丢失下的基准确认和元数据依赖，以及服务端和网络部署。能力与维护成本未核对前不选定库，不在本轮启动迁移。

## 8. 测试数量与验收讨论

复用既有协议、客户端session、服务器连接/Outbox、历史姿态用例和S3-E2。先补现有断言；只有新状态机存在无法合理承载的关键缺口，才另行说明新增依据。当前不新增永久用例。

| 阶段 | 最少需要的直接证据 |
| --- | --- |
| 测量校准 | 无故障参考＋60 Hz的1%丢包、0.9秒短断网；保留原版与候选同环境、同方向成对记录、实际故障时刻和传输统计 |
| 时钟候选 | 纯输入验证尖峰、持续变慢、迟到/重复pong及清理；复测上述两点，并补30 Hz短断网，检查真实年龄、偏移误差与操作进展 |
| 发送窗口候选（若进入） | 150 ms RTT防止窗口压低同步，短断网与限速检查恢复/有界退出，5+5或1+9验证健康连接隔离；仅改这里所需参数 |

丢包结果若单轮不稳定，最多先登记3组交错顺序、固定种子的成对窗口作方向筛查，报告每轮和范围，不宣称3组就有统计显著性，不通过反复重跑挑最好结果。证据不足则标不确定，回到归因；短断网先对齐实际故障时刻。扩大窗口时必须重新核对真实开火、换弹、备弹和对局未结算，不能只延长等待。

每条原子用例仍能独立准备与清理，不依赖手动服务或其他用例顺序。达到目标就停止增加机制；不重跑旧32真人矩阵，不重复与改动无关的浏览器/视觉组合。

**验收口径需要单独决定。** 现行“年龄p95/p99相对基线最多多一周期”仍生效，旧失败仍待验。本方案建议把可信时间基准、故障恢复时间、持续停顿和真实操作进展放在主要评估位置，避免把一个8秒、受时钟估计影响的分位数作为唯一优化方向。新增观测先不取代旧门槛；如果校准后证明原相对线缺乏稳定的体验含义，应向用户提出具体替代标准再确认，不能在实现中悄悄放宽。

## 9. 建议确定的执行顺序

先确定“测量校准→两端时钟/RTT”两步；发送窗口只在证据满足时进入，插值/批量处理与新传输继续作为后备。当前不扩容、不增加压缩等级、不改回溯或玩法规则。这条路线先处理代码中明确存在的估计与匹配问题，同时给真实TCP恢复瓶颈留下清楚的停止和转向条件。
