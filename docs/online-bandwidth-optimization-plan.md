# 联网带宽优化调研与方案

日期：2026-11-14起，2026-11-15调整容量范围。状态：O1—O3软件实现完成；按用户决定，当前只要求单房最多10真人或最多两房合计10真人以内达到整体指标，不再保证两房32真人。该范围的8个本机直接容量窗口通过；原相对弱网待验项保留，目标服务器与真实设备仍待验。六项审查约束保留；实际证据见[实施记录](online-bandwidth-test-results.md)。

依据：[产品设计](online-product-design.md)、[技术方案](online-technical-design.md)、[开发约定](development-guide.md)及 [S5 本地记录](s5-test-results.md)。本文补充带宽优化的候选、顺序与验收方法，不替代现行产品合同，不表示 S5 已通过或进入 S6。

当前剩余弱网问题的调研与候选顺序见[弱网优化方案草案](online-weak-network-optimization-plan.md)。该草案尚未执行，不改变本方案现行门槛或待验状态。

## 1. 目标与边界

降低每位玩家的持续收发流量和整房出网，并避免把带宽开销转成不可接受的 CPU、内存、排队或维护成本。首选适合当前规模的简单方案，达到目标后停止增加机制。

本方案保持以下约定：

- 4v4、5v5、8v8，团队竞技与中继争夺，机器人补位及对局中加入。
- 服务器权威；模拟和输入保持 60 Hz，连续状态同步保留 60/30 Hz 两档。
- 公共状态与本人校正在同一快照边界应用；客户端显示与服务器历史命中姿态可配对重建。
- 暂停、恢复倒计时、输入中断、生命与阶段切换、事件去重和房间隔离保持现有语义。
- 在线和离线继续复用规则；网络优化不要求离线入口使用编码、延迟缓冲或连接。
- 首选 WebSocket 与现有单进程结构。真实设备与目标服务器验收仍按已有安排单列，不由自动化结果替代。

后文的字节预算、数值容差、实验时长和候选格式均为建议，随对应阶段的[测试设计](online-bandwidth-test-plan.md)细化。早期调研仅改文档；用户现已授权实现，编码选择、版本和检查结果以实施记录为准。

## 2. 当前证据与问题定位

### 2.1 每人带宽的参考量级

UNSW 的 2022 年研究分析了包括 CS:GO、Fortnite、使命召唤在内的游戏，指出典型射击游戏通常只需几百 kbps。[研究原文](https://www2.ee.unsw.edu.au/~vijay/pubs/conf/22pam.pdf)

Respawn 在 2021 年说明，当时 Apex 的 20 Hz 同步在开局约消耗 60 KB/s，约合 0.48 Mbps；相同状态量若升到 60 Hz，推算约为 180 KB/s。后一个数值是推算，不是已测的 60 Hz 运行结果。[官方说明](https://www.ea.com/games/apex-legends/apex-legends/news/servers-netcode-developer-deep-dive)

这些历史资料说明量级与频率的关系，不构成当前所有 FPS 的平均流量、最低接入带宽或本项目必然能达到的压缩比。语音、下载和视频串流不与对局状态流量混算。

### 2.2 S5 的 16 人基线

来源：每个报告的 `levels[0]`，单房间、16 名真人、16 个角色。工具使用实际服务器和 OnlineSession，但没有渲染与预测物理。每级预热 2 秒、测量约 6 秒，属于本地短时工程样本。

| 档位 | 每人应用下行 | 每人应用上行 | 整房 socket 出站折算 |
| --- | ---: | ---: | ---: |
| 60 Hz | 845.6 KB/s，6.76 Mbps | 22.8 KB/s，0.182 Mbps | 约 108.0 Mbps |
| 30 Hz | 452.3 KB/s，3.62 Mbps | 22.8 KB/s，0.182 Mbps | 约 58.0 Mbps |

KB、Mbps 均为十进制。每人应用字节/秒按 `sum(generated.bytesIn/bytesOut) / server.elapsedMs × 1000 / humans` 计算，再除以 1000 得到 KB/s、乘以 8/1000000 得到 Mbps。socket 与应用计数的窗口边界略有差别，不强求二者精确相等。socket 计数含 WebSocket 数据，未包含 IP/链路头和重传，不能视作公网线速。

原始报告：[60 Hz](../artifacts/online-s5/20261114/capacity-current/S5-E1-60-humans/report.json)、[30 Hz](../artifacts/online-s5/20261114/capacity-current/S5-E1-30-humans/report.json)。原构建与最终构建的关系见 [S5 来源说明](s5-test-results.md#来源复现与待验项)。两档运行中的动态状态不完全相同，不能据此推导单纯降频的精确收益。

### 2.3 开工前的链路与当前选择

- 开工时[消息编码](../src/protocol/messages.js)为 JSON；[WebSocket 服务](../server/app.js)设置 `perMessageDeflate: false`。
- [房间发布](../server/rooms/sample-room.js)每次发送全体角色公共状态，加上该接收者完整的本人校正。公共部分只编码一次以节省 CPU，网络仍向每个真人发送一份。
- 角色昵称、阵营和控制类型已经移入初始化及成员变化时发送的 roster。这项优化已经存在，不能重复计作未来收益。
- [活体姿态](../src/sim/pose-sample.js)发送重建参数；尸体则每个快照发送身体旋转和全部 19 根骨骼的位置、旋转。
- [本人校正](../src/sim/actor-state.js)发送完整预测状态、各武器状态、随机状态、受击状态等；`activeInput` 还带有完整输入帧。
- 暂停与倒计时阶段，房间发布条件绕过同步档位，每模拟步都发送完整快照，因此 30 Hz 档也可能在这些阶段发送 60 次/秒。

早期实验二进制 [codec.mjs](../scripts/s3/codec.mjs)是逐包字段字典、类型标记及 int32/float64 的通用对象编码，没有定制字段布局、数值量化或差量，也未接入正式链路。[S4 复测报告](../artifacts/online-s4/20261114/matrix-current/S3-E1/report.json)中，它只减少约 26% 字节且编解码更慢。这个结果只淘汰该候选，不能证明专用二进制不适用。

当前实现已经选择专用二进制协议9：公共几何与动画phase使用既定误差网格，分支敏感值、输入和完整本人校正保持精确；公共状态相对已确认基准作XOR，公共体和完整本人校正使用独立有界raw DEFLATE块。服务器以原生zlib level6/memLevel4压缩，浏览器以锁定fflate解码。每约500 ms及必要生命周期边界提供全量，基准最多两份，缺失时按次数和时限恢复。普通shot广播省略经消费者审查的五个回溯诊断字段，服务器权威事件仍保留。PMD继续关闭、无压缩异步队列、无缓冲池。完整合同见[阶段测试设计](online-bandwidth-test-plan.md)，验证状态见[实施记录](online-bandwidth-test-results.md)。

### 2.4 已有样本中的开销分布

本轮只读分析既有 [60 Hz 语料](../artifacts/online-s4/20261114/matrix-current/S3-E1/corpus-60.json)与 [30 Hz 语料](../artifacts/online-s4/20261114/matrix-current/S3-E1/corpus-30.json)。其中分别有 32/22 个完整快照，均为 8 角色，含运行与倒计时阶段，不能代表 S5 的 16 人、按实际持续时间加权的流量组成。

| 分区 | 快照字节占比 | 本项目判断 |
| --- | ---: | --- |
| 姿态参数 | 29.4% / 29.5% | 字段与数值表示值得优先压紧，保留姿态重建关系 |
| 尸体骨骼字段 | 13.7% / 14.2% | 开销随死亡人数变化，需单独覆盖集中死亡 |
| 其他公共角色字段 | 29.4% / 29.3% | 坐标、速度、状态、战绩等；先紧凑表示，再考虑变化发送 |
| 本人校正 | 23.3% / 22.8% | 必要字段较多，适合固定布局，删减须有重放证据 |
| 包头、场景和结构开销 | 4.2% / 4.2% | 先保留，避免围绕小头部做复杂优化 |

两档样本平均完整快照均约 8.2 KB。统计用 UTF-8 JSON 字节：本人分区计其对象；姿态与尸体分区计字段名、冒号、值及相邻逗号；其他角色分区为角色对象的剩余；其余归末项，各分区互斥。百分比四舍五入。它用于确定优化顺序，不用于承诺压缩后大小。

## 3. 常用手段与适用性

Epic 将不必要同步、更新频率、休眠、相关性筛选和量化列为优化方向，并建议从必要数据及可推导状态入手。[官方建议](https://dev.epicgames.com/documentation/unreal-engine/performance-and-bandwidth-tips-for-unreal-engine)

下表的“适用性”是结合本项目规模和合同的判断，不是照搬引擎配置。

| 手段 | 常见做法 | 对我们的适用性与代价 |
| --- | --- | --- |
| 减少必要数据以外的同步 | 静态参数本地读取，元数据初始化发送，移除未消费的诊断数据 | 高；先列消费者与重建依据。地图、武器定义和 roster 已有本地或低频来源，不能重复计算收益 |
| 固定布局、编号与位打包 | 不逐帧发送字段名；枚举用编号，布尔组合为位标志 | 高；适合稳定的输入、公共快照与本人校正，先做无损候选 |
| 数值量化与压缩旋转 | 按范围和容差编码坐标、角度、姿态，四元数减少分量 | 公共状态适用性高；预测状态更谨慎。精度、范围及越界处理必须逐项验证 |
| 变化掩码与差量 | 相对已知基准只发送变化字段或小数值差 | 有条件；活跃姿态仍常变化，不能假定节省固定比例；增加基准、确认与恢复状态 |
| 静态状态分块、休眠 | 未变化的对象或字段不持续发送，唤醒时补齐 | 暂停状态适用；战绩等可后置评估。活人和机器人均参与命中，不能仅按控制类型休眠 |
| 多档频率和优先级 | 重要对象高频、背景对象低频 | 暂停与纯表现数据可评估；活体仍遵守现有 60/30 Hz，不引入按距离改变命中姿态频率 |
| 兴趣区域、可见集 | 只向客户端同步相关对象 | 当前优先级低；地图小、最多 16 角色，还需处理角色碰撞、声音、手雷、雷达和据点，筛选成本与漏同步风险较高 |
| 事件与参数重建表现 | 发送出生参数、动作时间或随机参数，在客户端重建轨迹与动画 | 已有规则可证明时适用；死亡动画是候选。不能把权威伤害、手雷爆炸或活体命中姿态交给客户端自行决定 |
| 消息合并和批量 | 合并同一时刻的事件，摊薄帧和调用开销 | 后置；先量化小消息占比。批量不得等待额外输入周期，不延迟开火、暂停或输入中断 |
| 通用压缩 | WebSocket permessage-deflate 等 | 有条件；实现接入较小，但增加 CPU、每连接内存及异步压缩等待，需真实负载对照 |
| 替换传输或同步架构 | 不可靠通道、状态外推、全场确定性输入同步等 | 本轮不选；它们影响浏览器、部署、补偿与模拟边界，不能代替先减少数据 |

具体参考：Unity 支持按字段量化以及未变化时不发送的静态同步模式；Gaffer 介绍量化、旋转编码和基准差量；Suroi 的实际浏览器游戏代码使用输入位打包与有界数值编码。这些机制可借鉴，原项目的精度与压缩比不能直接套用。[Unity 1.5 文档](https://docs.unity.cn/Packages/com.unity.netcode@1.5/manual/ghost-snapshots.html)、[Gaffer 快照压缩](https://gafferongames.com/post/snapshot_compression/)、[Suroi 输入](https://github.com/HasangerGames/suroi/blob/master/common/src/packets/inputPacket.ts)、[Suroi 数值编码](https://github.com/HasangerGames/suroi/blob/master/common/src/utils/suroiByteStream.ts)

## 4. 推荐方案：先建立紧凑完整状态

先保留完整动态快照及现有配对关系，减少表示与重复数据。新协议的网络对象与核心存档对象可以不同，但字段映射集中维护，不复制另一套规则。低频控制消息可以继续用 JSON；高频输入和快照采用选出的紧凑格式。客户端和服务器只维护一个正式高频格式，JSON 留作实验对照或有界诊断输出。

### 4.1 数据职责

| 数据 | 建议处理 | 必须保留的关系 |
| --- | --- | --- |
| 地图、骨架和武器定义 | 使用构建/规则版本一致的本地定义；证明恒定的字段才省略 | 不用席位或数组下标冒充持久角色身份 |
| 成员元数据 | 沿用 roster 与版本引用 | 初次加入及同一连接再入场完整初始化 |
| 位置、速度、朝向和活体姿态 | 60/30 Hz，先固定布局，再逐项验证量化 | 同一时间边界；显示与历史使用同一解码值 |
| 血量、弹药、保护、雷达、战绩、据点等 | 第一轮保留在完整状态中，紧凑编码 | 后续仅在收益明确时拆版本块或做差量，不能只发一次事件后永久失去自恢复能力 |
| 本人校正 | 配对快照发送必要的完整重放状态 | 权威确认、沿用输入、冷却、随机及受击状态一致 |
| 尸体 | 与活体分支编码；先压紧绝对姿态 | 生命切换、死亡姿态、暂停及中途加入正确 |
| 射击、受击、成员、阶段与结算事件 | 保留真实客户端所需字段和稳定编号；诊断字段审查消费者后移出普通广播 | 即时事件不额外改变远端可命中骨骼，不重复扣血或计分 |
| 暂停、倒计时和时钟 | 阶段切换立即发送完整状态；稳定期间评估低频轻量同步 | 恢复截止时刻、连接存活与加入离开及时，旧输入不跨阶段生效 |

不优先从公共快照排除接收者自身角色：这会破坏公共编码复用，当前预测也读取公共角色样本。先让这一份状态变小，再判断重复字段是否值得改造。

### 4.2 格式选择与无损基线

只保留少数能回答问题的候选，不对所有序列化库做横向选型：

| 候选 | 用途 | 选择条件 |
| --- | --- | --- |
| 原完整 JSON | 现有基线 | 不缺字段，作为字节和语义对照 |
| 固定数组/编号的紧凑 JSON | 低成本对照，区分字段名与数值文本的贡献 | 若已达标且维护更简单，可优先选择 |
| 专用二进制完整包 | 推荐主候选；固定顺序、数值字段、枚举和位标志 | 在实际大小、编解码、校验与维护成本上有净收益后采用 |

结构精简后的完整状态若仍超预算，可在正式格式接入前，把“紧凑 JSON 加原生 WebSocket 压缩”纳入一次小范围对照，使用第 5.1 节的成本与正确性门槛。无需先完成整套专用二进制再比较更简单的可行路径；若这个候选已满足全部目标且维护更少，可以直接采用并跳过不必要的量化或差量。对照候选不表示开启当前默认。

第一轮二进制保留浮点字段的完整精度，不把 float32 当作无损替换；整数与布尔保持精确。它用于建立可解释的结构收益，量化另测。可选字段用明确的存在位，不能混淆缺失、零、false 和 null。

MessagePack 的 map 仍携带键，改成 array 才能省去字段名；Protobuf 用字段编号，并提供整数变长与浮点表示，但增加 schema、运行库或生成流程。它们不会自动解决重复全量发送。[MessagePack 规范](https://github.com/msgpack/msgpack/blob/master/spec.md)、[Protobuf 编码](https://protobuf.dev/programming-guides/encoding/)

当前不预设引入这些依赖。若专用编解码出现明显维护成本，再选一个成熟库与同一字段表比较；库更简单可靠时采用库，不为手写格式坚持额外复杂度。

高频包包含明确的类型/格式版本、房间与快照身份、模拟 tick、必要时钟/阶段字段和角色数量；公共部分与本人校正一起校验、原子应用。编号先覆盖现有范围，不为少几个字节擅自缩成 8/16 位：角色替换、长暂停和长连接会使编号增长。时间字段保留单位及合法范围。

未来改版时更新游戏协议版本与构建标识，不允许新旧格式混用。同一版本默认只选定一种正式布局，不增加玩家可见的编码选择或运行时自动切换。

### 4.3 活体姿态与公共数值量化

逐项记录字段范围、编码、最大误差、越界策略、消费者及验证证据：

| 字段 | 初始候选 | 拒绝或回退条件 |
| --- | --- | --- |
| 公共位置 | float32 与 1 mm 步长的有界整数分别比较 | 地图边缘、楼梯、碰撞或命中误差超预算；不得静默夹取合法位置 |
| 公共速度、姿态连续参数 | 不参与关键分支的字段先比较 float32，再对有界字段尝试定点数；分支敏感字段先保留原精度 | 重建的骨骼或碰撞误差超预算，或改变应保留的条件分支；不照搬其他演示删除速度 |
| 公共朝向 | 有界角度编码，处理环绕 | 头胸四肢的实际世界坐标偏差超预算 |
| 姿态 `dt` | 仅经证明的值用枚举或推导 | 出生首次样本可为 0，不能一律写死为 1/60 |
| 时间、计数、生命和阶段 | 整数保持精确；时钟与冷却先保精度 | 不因编码改变新鲜度边界、保护截止、连射或换弹生效步 |

候选筛选先以公共位置每轴误差不超过 0.5 mm、姿态重建的命中盒顶点最大偏差不超过 2 mm 为起点；是否足够须用实际地图、武器和姿态验证，不能当作已经验证的容差。无法安全压缩的字段保留更高精度。

量化准入同时检查条件分支。现有 [姿态算法](../src/sim/character-pose.js)包含 `speed > 0.3`、`fwd < -0.3`、`crouchK > 0.5` 等判断；`Math.fround(0.3)` 约为 `0.3000000119`，足以使第一个比较翻转。输入值误差很小，不代表动作或命中盒误差很小。这是代码与数值审查确认的候选风险，当前二进制链路保留这些分支敏感字段的完整精度。

字段表须标出影响的分支与阈值，验证阈值内、阈值处、阈值外，以及两端点之间的插值过程。关键分支先要求与未量化值一致，再检查完整姿态、射线和碰撞容差；无法保持时该字段保留原精度。不得为了让编码候选通过而移动核心阈值、夹取数值或改变姿态规则。已有姿态与历史用例优先承载这些边界，不因每个阈值新增一条独立用例。

射击视角不直接沿用公共朝向精度。例如 16 位覆盖一整圈时，最大角误差约 0.00275 度，100 m 处可对应约 4.8 mm 的横向偏差。必须按实际有效射程检查，不能只看角色附近的误差。首轮输入视角保留完整精度。

关键改造点位于 [publish](../server/rooms/sample-room.js) 与 [历史存储](../server/sync/history.js)：开工时历史先存原始值，再编码发出。当前已从同一规范化流程产生网络状态与历史状态，历史使用量化后可解码的公共值，客户端插值同一组值。服务器权威对局仍按原精度计算，不因此量化整个模拟或离线规则。

这是本项目的同步约束，不能直接套用“所有模拟每步一起量化”。Gaffer 对外推型状态同步说明了数值差异反馈到模拟时的精度风险，但我们的默认路径仍是公共快照插值与本人预测。[状态同步与量化讨论](https://gafferongames.com/post/state_synchronization/)

### 4.4 本人校正与输入

本人校正优先省字段名、编号、明确恒定的参数与可证明的重复值；继续集中使用现有保存/恢复字段定义。各武器的冷却、弹药、散布、规则随机状态和受击偏移影响后续重放，不能因为当前未持有就删除。是否变化发送留到差量阶段。

输入保持每秒 60 个操作帧。先无损打包按钮、动作、切换槽位、编号和已有显示引用，保留创建时间、新鲜度、生命与阶段、一次性按下和沿用输入的语义；不改成“有变化才发送”，也不等待积攒多帧。

如以后量化输入角度或移动轴，必须在本地预测之前产生规范化输入；本地预测与网络发送消费同一值。不能在 [prediction.submit 之后的 send](../src/client/online-game.js)才改变数值。显示引用的 alpha 同样先保精度，避免服务器重建的姿态与真实画面样本不一致。

### 4.5 尸体处理

第一步采用活体/尸体分支，只发送该分支实际需要的字段；确认消费者后省去尸体上遗留的活体姿态参数。静态骨架局部位置可引用共同定义，变化位置和旋转显式编码；先验证 float32，再评估更紧凑的旋转表示，不直接改变死亡表现算法。

如果尸体仍是主要开销，再比较两条路径：紧凑绝对姿态继续同步；或死亡初始化加固定步重建。后者至少需要初始必要骨骼状态、死亡随机参数、动画时间/步数及一致算法，不能只发死亡时间、随机种子或让客户端重新随机。当前 [updateDeath](../src/sim/character-pose.js)包含依赖上一步姿态的迭代更新，不能假设任意时刻凭几个参数即可无状态求值。

尸体停止同步或降低频率只能基于表现和生命周期证据。加入时必须能恢复当前尸体，暂停冻结动画时间，复活后旧尸体状态不跨生命复用。活体与尸体分别统计字节及误差，避免用全员存活样本掩盖集中死亡峰值。

### 4.6 暂停与倒计时

当前选择保留既有配对快照与阶段发布语义，由公共差量和块压缩减少冻结数据；独立轻量脉冲作为后续候选，尚未引入。达到联合预算后按停止条件收敛，不为此另加阶段协议或测试组合。

建议阶段切换时立即发送完整配对状态，稳定暂停时停止反复发送冻结角色；倒计时主要同步权威的 `resumeAtMs`。可从与现有 1 Hz 时钟采样配合的轻量脉冲起测，不把该数值直接当成最终配置。

这需要一并设计客户端的状态新鲜度判断、模拟 tick 对齐、输入确认和插值缓冲。当前客户端依赖完整快照到达更新新鲜度，不能只让服务器少发包，否则长暂停恢复时可能被误判超时。暂停中加入/离开、取消倒计时及结束仍立即发布对应状态，恢复时重新建立当前边界，旧输入保持失效。

### 4.7 模块影响与接入边界

| 位置 | 后续可能承担的改动 | 审查重点 |
| --- | --- | --- |
| `src/protocol/` | 字段布局、数值规范化、编解码、范围与版本校验 | 无对局或设备副作用；格式与量化定义供两端共用 |
| `server/app.js`、`server/transport/` | 区分文本/二进制接收，支持对应发送类型与真实字节计数；可选压缩的有界配置 | 当前入站会直接转字符串，不能只替换 encodeMessage；保留输入校验、消息上限和慢连接隔离 |
| `server/rooms/`、`server/sync/` | 公共编码复用、私有配对、规范化历史；按需维护差量基准 | 核心仍拥有对局状态；不同房间与连接的可变缓存隔离 |
| `src/net/` | 浏览器设置二进制接收方式，统一解码与原子应用；轻量同步或基准恢复 | 优先 ArrayBuffer，避免 Blob 异步转换改变消息处理顺序；限制缓存并完整清理 |
| `src/client/` 与必要的纯状态投影 | 若需要，在预测前规范化输入；从统一状态驱动画面 | 不把网络编码写入规则，不让即时事件修改远端命中姿态 |
| 现有测试与实验工具 | 扩展对应格式、指标和证据身份 | 测实际链路，不保留一条只有实验工具能运行的优化路径 |

如果最终选择 JSON 或原生压缩，跳过无关的二进制接入改造。实验候选不全部进入正式构建；格式可读性由有界诊断解码提供，不要求玩家或离线入口理解协议。

### 4.8 快照、基准与发送缓冲的所有权

已提交到服务器历史、客户端插值缓冲、预测碰撞引用或差量基准的完整状态均按不可变值使用，包括嵌套数组和骨骼数据。解码新包或应用差量时产生一份新的完整状态，经校验后原子提交，不原地覆盖旧快照或旧基准。允许共享已证明只读的数据，不要求无差别深拷贝；任何共享都必须保留完整的引用生命周期。

二进制消息交给发送或异步压缩后，其底层缓冲在所有相关发送真正完成或已确认取消、且不再被其他使用者持有前，不得修改或归还复用池。同一公共缓冲服务多个连接时，必须等待所有持有者释放，不能以最快连接的完成回调为准。第一轮优先使用独立消息缓冲，不引入复用池。

现有 [Outbox 的 onSent](../server/transport/outbox.js)在调用 `socket.send` 后立即执行，只表示已交给发送接口，不表示压缩、写出或客户端解码完成，不能据此复用缓冲或确认差量基准。尚未交给下游的替换快照、已经排队的发送以及历史状态分别清理；异步回调只释放本次操作拥有的资源，不修改已切换到新房间或阶段的状态。

验证复用现有 Outbox、预测和历史用例：提交后处理下一包不改变旧状态；慢发送与快照替换不改写在途字节；多接收者及失败清理不提前释放共享缓冲。只在实际选择二进制或差量时增加对应断言。

## 5. 按证据进入的可选机制

### 5.1 通用压缩

在紧凑完整状态仍未达标时，比较不开压缩与 `permessage-deflate`；第 4.2 节允许在正式格式接入前就对同一完整状态做这项小范围比较。当前默认保持关闭，不能只根据离线压缩率决定上线。

RFC 7692 的上下文接续可以复用前一条消息的字典；关闭接续有利于约束跨消息状态与内存，开启可能提高相似消息的压缩率。[RFC 7692](https://www.rfc-editor.org/rfc/rfc7692)

先测一个有界的无上下文候选；只有结果显示需要跨消息收益时才比较接续。约束压缩级别、窗口、并发和小消息阈值，验证浏览器实际协商的参数。[`ws` 官方文档](https://github.com/websockets/ws#websocket-compression)提示 CPU、内存及高并发下的碎片化风险，尤其需要在实际部署系统验证。

服务端开启选项不等于每条连接都协商到压缩。未协商到扩展时，WebSocket 可以正常建立并传输未压缩消息；同一正式应用格式必须继续正确工作，不能静默切换另一种游戏协议。[RFC 7692 协商规则](https://www.rfc-editor.org/rfc/rfc7692)

实验按连接记录实际协商结果和参数，将已启用与未启用压缩两条路径分别验收功能、同步质量和真实字节。通过客户端不提供扩展或服务端关闭扩展构造必要对照，不只验证默认协商成功的路径。若某条仍受支持的路径超预算，则记录该路径未达标并继续评估格式或数据结构；不能把其流量混入平均值，也不能为达标擅自拒绝已有支持范围内的客户端。确需改变支持范围时按第 1 节边界讨论。无扩展是正常路径，非法协商或压缩协议错误仍按连接错误处理。

必须统计每连接压缩状态、异步任务和排队，保证在选定的实际发送消息上压缩；已经进入 ws 压缩/发送队列的旧消息无法由 Outbox 替换。公共 JSON 编码可以复用，不代表带私人校正和连接压缩上下文的消息能跨连接共用压缩结果。

应用包体和解压后大小都需有限制，清理覆盖断线、离场、结算和服务停止。O3中紧凑全量仍未达标，已取得应用层独立raw DEFLATE块的必要性证据，选择成熟fflate 0.8.3（MIT）与原生zlib互操作，而未开启PMD。两端共同执行同一有界格式，无扩展是正式路径；不另留协商压缩分支。先前暂缓额外解码依赖的决定由此更新，不同时引入gzip/Brotli/LZ4/WASM链路。压缩等级、块上限、许可和独立互操作验证见阶段测试设计。

### 5.2 变化块与差量

先比较轻量变化块，再考虑逐字段数值差。相对基准未变化的字段可以省略，已变化的位置可以发送紧凑绝对值，不必一开始就做多级位编码。连续变化的移动和姿态仍占空间，量化和差量的收益不能简单相加。

静态/低频块若独立发送，快照必须引用明确的块版本，并在所有依赖齐备后按该快照边界应用；加入时补齐完整状态。不能仅按“消息已经到达”立即改变插值中的过去状态，也不能把必要更新放进可随意丢弃的消息链。

对于快照差量，建议：

1. 全量关键帧建立基准；差量带当前 `snapshotSeq` 和明确 `baseSeq`。
2. 以客户端已完整解码、验证并加入缓冲的状态确认基准；确认可随输入或轻量脉冲携带。它不代表该快照已经显示，不能替代真实显示引用，也不复用输入执行确认 `ackSeq`。
3. [Outbox](../server/transport/outbox.js)会替换尚未发送的快照。差量不能依赖上一份生成后被替换的消息；始终相对该连接已确认的基准生成可独立应用的更新。
4. 缺少基准、依赖不齐或校验失败时不应用半份状态，使用有界的完整快照恢复；限频恢复请求与关键帧，避免恢复风暴。全量恢复也是正式路径的一部分，计入带宽。
5. 入场、离场、结算、换房与阶段切换清理相应基准；成员替换与生命变化完整替换对应角色，不能跨生命拼接。
6. 基准、候选历史和确认队列按连接设上限，拒绝伪造或越界确认。服务端的“已发送引用集合”不是“客户端已解码确认”。

基准保留与淘汰另有以下约束，仅在确定采用差量后落实：

- 差量解码基准与显示缓冲、命中历史承担不同职责，不能直接套用当前显示缓冲的最近 32 帧淘汰策略。可以共享不可变状态，但保留条件分别管理。
- 客户端确认新基准 B 后，服务器可能尚未收到确认，仍会发送依赖旧基准 A 的消息；发送 ACK 本身不允许客户端释放 A。已向服务器确认的候选也不能在服务器可能选用时静默淘汰。
- 推荐在同一房间和阶段内单调推进服务器采用的基准，并按快照序号提交发送。客户端成功应用首个明确采用 B 的消息后，只有在有序链路和单调切换保证后续不会再依赖 A、且其他使用者也已释放时，才淘汰 A。异步编码不得把更旧的基准消息排到切换之后；若不采用这项保证，必须设计等价的显式切换确认后才能释放。
- 接近容量上限时，先限制新增确认候选或启动有界的全量重建，保留仍可能被引用的基准。释放采用明确的切换或重建边界，不以覆盖旧槽位的方式等待解码失败；等待与重建也须有超时和失败退出规则。
- 重复、迟到和越界确认不能使基准倒退；入场及阶段边界按前述规则重置。关键帧与差量均遵循第 4.8 节，不原地改写旧状态。

O3 的测试方案先确定缓存数量/字节、待切换保留期限和恢复次数/时限，再比较候选。复用替换、生命周期和客户端用例补强“确认延迟、旧基准接近淘汰、切换时仍有在途消息、容量触顶后恢复”的直接证据；不为尚未选用的差量建设额外缓存或用例。

这是针对当前替换队列的选择。WebSocket 的可靠有序传输可以支持其他严格维护发送依赖的设计；它无法恢复应用层主动丢弃的前置状态。已确认基准是较容易审查的候选，不是所有可靠传输都必须采用同一 ACK 设计。[差量与基准原理](https://gafferongames.com/post/snapshot_compression/)

差量可能失去每房间公共包只编码一次的优势，额外增加每连接比较、内存与历史保留。只有紧凑全量仍存在明确瓶颈，且这些成本后仍有净收益时进入。

## 6. 预算、比较方法与停止条件

### 6.1 拟定的第一轮目标

| 指标 | 建议目标 | 范围 |
| --- | ---: | --- |
| 60 Hz 每人持续下行 | ≤1.0 Mbps，125 KB/s | 8v8 满房，对局状态、本人校正、事件及常规控制消息合计 |
| 30 Hz 每人持续下行 | ≤0.6 Mbps，75 KB/s | 相同必要状态，不把低档变为不同玩法 |
| 每人持续上行 | ≤0.08 Mbps，10 KB/s | 两档都保持 60 Hz 操作语义 |
| 保证范围总持续出网 | 对应约 ≤10.0 / 6.0 Mbps | 单房或两房合计最多10真人，同一socket计数口径的算术预算，不是公网线速或目标机容量承诺 |

目标先按服务器每连接 socket 收发字节计数，窗口内计入 WebSocket 帧与实际压缩后的数据；排除页面下载与首次握手并单独报告。IP/链路头、重传、TLS 开销和带宽余量在目标部署测点另列。保留原始逻辑消息字节和压缩前编码字节，解释收益来自哪里，不能启用压缩后仍用 JSON 长度代表实际出网。

持续目标要求每位玩家的完整窗口平均值与非重叠 1 秒窗口 p95 均不超过相应预算，任一超限均不能判该负载达标，不以全房平均掩盖个别连接。普通交火、死亡和复活计入对局窗口；集中加入、强制恢复等突发另列每次字节、1 秒峰值、状态恢复时间和队列峰值，不能藏在预热阶段，也不能只看 p95 忽略最大值。

带宽、同步质量和实际负载联合判定。只减少成功交付的状态、延迟处理、断开玩家或使负载空转，不计作优化收益：

| 指标 | 通过约束 | 实施前固定的内容 |
| --- | --- | --- |
| 正常网络的有效同步频率 | 按每人成功解码、验证并原子应用的不同常规快照计数；建议沿用 S5 的 59/60 模拟容差，60 Hz 档≥59 次/秒，30 Hz 档≥29.5 次/秒 | 对应档位与有效运行窗口；阶段切换的额外快照、重复包、心跳、解码失败和缺基准的包不补足计数 |
| 快照新鲜度 | 同环境对照，候选 p95/p99 状态年龄不超过基线对应分位加一个同步周期；并满足事前登记的绝对上限 | 按正常与各弱网预设登记状态年龄、最长无有效状态持续时间的毫秒上限，不只看均值 |
| 队列与处理 | 编解码、压缩等待和发送队列均有界，最旧未处理状态年龄不超过登记上限；不增加策略性的攒帧等待 | 数量、字节与队列年龄上限、超限时合并/停止/退出规则；消息变小后重新校准字节上限，不靠放宽回溯或显示缓冲掩盖延迟 |
| 突发流量 | 单次关键帧、单连接与整房 1 秒峰值均不超过本场景登记预算，且同步质量仍满足要求 | 最大消息字节、加入/恢复人数及速率、1 秒峰值上限和测量窗口；不能只有峰值记录而无失败标准 |
| 加入及全量恢复 | 从请求到完整当前状态原子提交的时间不超过登记时限；超过次数/时限则明确失败或结束会话，不无限等待 | 两类操作分别登记计时起止、毫秒时限、请求/重试上限及失败动作；合法暂停不被当作运行态恢复 |

有效同步率与状态年龄按运行阶段分段统计，暂停轻量脉冲单列。连接心跳或时钟回复不能刷新运行态的快照新鲜度，避免“连接还活着”掩盖状态停滞；暂停恢复从新的完整状态边界重新判定。

除已列出的建议数值外，其余绝对上限由对应阶段测试方案先登记为具体数字，注明来源于现有配置、产品边界或独立基线预采。基线预采只用于收敛阈值；正式候选验收前必须填齐，未填或未测均不能判通过，不能根据候选结果事后放宽。本轮未执行预采，不编造尚无依据的延迟、突发或恢复数值。

按预算倒推，60 Hz 的全部消息平均每次更新约有 2.08 KB，30 Hz 约 2.50 KB；快照还要为事件和控制消息留空间。这是设计预算，不是已经得到的包体大小或压缩效果。

### 6.2 同状态对照与代表场景

先用一份有构建标识、规则、种子、生命周期标签和哈希的完整消息语料比较编码。既有 8 角色语料只供初筛；正式比较补采真实 16 角色和完整输入/事件，保留活体运动、换枪换弹、受击、尸体、手雷与据点。不能以字段更少、动作更少或不同尸体数量的小包冒充编码收益。

再以真实连接验证端到端影响。单房测点用于主要候选比较，多房测点只对选定候选复核当前开发上限与组合成本：

| 测点 | 必要负载 | 验证目的 |
| --- | --- | --- |
| 单房出网 | 1房、10真人+6机器人 | 在8v8席位下覆盖真人上限和公共状态/本人校正/AI的共同成本 |
| 单房高机器人占比 | 1 房、1 真人+15 机器人 | AI 与同步的共同预算，避免只测真人输入驱动 |
| 两房均衡分配 | 2房、各5真人+11机器人 | 总10真人、32角色，验证进程共享CPU/出网与两房隔离 |
| 两房偏斜分配 | 2房、1+9真人，分别15+7机器人 | 一个房间机器人密集，另一房接收者密集；验证单真人房释放后其他房继续 |

上述测点复用 S5-E1 的负载选择，覆盖两档，不为每个早期编码候选重复全部压力测量。集中死亡、暂停恢复和加入作为对应风险的必要片段；在一个选定的多房测点中加入慢连接，检查健康连接的有效同步率、状态年龄及控制响应，测量全局队列与内存，并验证受损连接释放后恢复。复用已有有效弱网证据，只有新机制引入的缺口才补测。

不为所有人数、玩法、武器、档位和网络参数做笛卡尔积。两种玩法和两档均有直接证据，其余组合按影响复用；负载测点和片段不另计为永久用例通过数量。

初筛只比较必要候选；最终候选建议预热至少 5 秒、采样至少 60 秒并重复 3 次，记录波动。稳定窗口不强制 GC；创建、集中加入与清理另测。延长测量是为纠正原 6 秒样本的局限，不为制造更多通过项。

延长窗口必须同时设计可重复的真实行为负载。现有 [S5 驱动](../scripts/s5/peer.mjs)持续提交开火输入；角色可以自动换弹，但长期存活仍可能耗尽备弹，因此不能只把 6 秒等待改为 60 秒，就认定保持了相同交火强度。驱动按真实操作和合法生命周期编排运动、开火、换弹、受击与复活；不逐帧直接补弹或绕过核心制造活动。

每个片段预先规定实际执行输入、有效射击、换弹及所需死亡/复活的次数或强度范围，并核对权威事件、状态变化及客户端成功应用的快照；合理的换弹、死亡等待仍计入规则负载。人数不足、提前结算、耗弹后长时间空转或生成器不足时，该窗口标为负载无效并保留原因，重新建立独立窗口，不能用低流量判候选达标。

测量窗口开始与结束均记录尚未完成的编码、压缩及发送工作，并做有界排空或明确结算在途字节，避免把推迟到窗口外的工作计作节流。丢弃、恢复重发和断线单独计数；其影响同时接受第 6.1 节的质量与恢复门槛约束。

记录真实消息及 socket 字节、全量/差量/恢复流量、输入实际频率、编解码和压缩耗时、端到端快照新鲜度、校正幅度、积压字节及持续时间、每房间和进程步进、事件循环、CPU、GC、内存与清理结果。语料压缩率不等于真实传输结果，Node 解码时间也不等于手机浏览器表现。

服务端沿用 S5 的本地筛选线：总步进 p95≤12.5 ms、p99≤16.67 ms、实际步进≥59 Hz、事件循环 p99≤33.33 ms。它不是目标机容量承诺。客户端数值与时序容差在对应实验前固定，不能测完后放宽以使候选通过。

### 6.3 进入与停止判断

- 紧凑完整协议达到预算、精度和时序要求后，停止增加差量、通用压缩、兴趣区域或自适应档位。
- 未达到预算时，按最新字节分布选择下一项，只解决仍存在的主要开销。比较实现和维护较少的可行选项，不机械叠加所有技巧。
- 新机制必须解决明确瓶颈，并在实际 CPU、内存、队列和体验上仍可接受；不能只凭压缩率选方案。
- 若继续优化必须改变支持范围、人数、权威规则、命中合同或既定同步档位，先记录证据与替代方案再讨论。
- 优化完成后按当前10真人保证范围复核S5；2房/32连接默认仅是开发准入配置，不代表32真人性能承诺，也不因理论节流自动扩大保证范围。目标机容量仍依赖实际证据。

## 7. 后续阶段安排

O 编号仅用于本优化，不替代 S1—S6 的状态。当前阶段与通过证据见实施记录；下表保留各阶段的范围与退出条件。

| 阶段 | 范围与产出 | 独立验收与进入下一阶段的条件 |
| --- | --- | --- |
| O1：必要字段与无损完整协议 | 字段/消费者表，代表语料，少数候选对照；选定并接入一种正式高频格式，保留无损输入与配对完整状态；压缩对照按进入条件选择 | 协议往返、错误输入、本人重放、不可变状态与缓冲所有权、生命周期及累计受影响检查通过；验收阈值已登记，对照负载有效；采用压缩时两条协商路径分别判定。若全部目标已满足，可直接进入 O4 |
| O2：主要开销量化与重复同步 | 公共规范化值同时供显示和历史；逐项数值压紧、尸体分支、暂停轻量同步及必要事件精简 | 关键分支的阈值与插值边界、骨骼/射线/碰撞及输入时序达到预设要求；两档真实流量与同步质量联合达标。达标即可进入 O4 |
| O3：按需的压缩或差量 | 对仍未达标的开销选择一个最小机制；必要时先做有界对照，不默认两者叠加 | 采用差量时证明基准确认、保留、切换、淘汰及有界恢复；采用压缩时证明协商路径、积压、全局并发与回收；均通过实际收益、质量和成本门槛 |
| O4：累计与 S5 复核 | 同构建完成正式预算、有效的持续交火、单房与两房负载、必要弱网、资源回收、受影响浏览器和离线检查；更新来源与记录 | 带宽与同步质量、突发及恢复联合判定，负载有效；本地优化结论与未验项明确，设备、目标机和主观体验仍按原门槛处理 |

每阶段先细化测试设计，独立实现、独立验证、累计回归通过后再开始下一阶段。O1 的软件退出条件不要求单独达成整体预算；未达标时记录差额并在本阶段必需检查通过后继续必要优化，不将阶段完成当作整体完成。

## 9. 实施前待收敛项

实施主线为“必要字段与紧凑完整状态 → 按需处理公共数值及重复同步 → 按需增加一种机制 → 累计复核”。以下事项随阶段推进收敛，未取得结果仍为待验证：

- 用完整 16 角色语料确认各字段、尸体与事件的真实占比，补足现有 8 角色样本的局限。
- 依据实际范围、分支阈值、骨骼和射程确定字段位宽及容差，保留不能安全压缩的状态；落实不可变状态与发送缓冲所有权。
- 以目标预算和维护成本选择正式格式；若简单候选已达标，取消更复杂候选。
- 在正式候选验收前填齐状态年龄、停滞、队列年龄、突发与恢复的数字门槛；补足有效持续交火及当前两房上限/混合负载，不能用少发状态或空转换取低流量。
- 若进入压缩，分别确定已启用与未启用路径的功能和预算结论；若进入差量，先收敛基准保留、切换与淘汰。两者均固定连接内存、恢复、排队与释放上限。
- 取得目标服务器与实际浏览器设备后，验证部署性能与体验；继续保留已有未验状态。

最初调研的文档检查只证明来源、算术、链接及现行约定一致；后续实现、性能、游戏测试与未执行的设备验收分别记入实施记录。
2026-11-15容量覆盖补充：两房各1真人、共30机器人，覆盖10真人以内的进程AI上界，不能只用单房高AI结果乘二推断。与单房10、两房5+5、1+9合计四种代表分配，两档共8窗，不新增永久用例。
