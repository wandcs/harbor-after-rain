## 2. 60Hz：夹具影响可量化，恢复主要仍在TCP层等待

本轮只测量既有执行顺序，**未移动恢复前同步读取qdisc统计的动作**。以下单位ms：

| 观测 | 原始参考 | 当前候选 |
| --- | ---: | ---: |
| 全丢命令完成→恢复命令完成 | 906.22 | 911.79 |
| 恢复前qdisc统计读取耗时 | 3.26 | 4.21 |
| 恢复命令自身耗时 | 3.90 | 10.51 |
| 恢复命令完成→下行缺口被覆盖 | 731.87 | 746.74 |
| 缺口覆盖→首消息进入JavaScript | 0.49 | 0.15 |
| 首消息解码/提交/预测 | 0.062 / 0.012 / 0.274 | 0.172 / 0.096 / 0.295 |
| 恢复命令完成→3个新鲜tick | 793.80 | 764.88 |
| 恢复命令完成→新输入真正执行 | 832.24 | 811.16 |
| 恢复命令完成→该执行获确认 | 832.95 | 812.54 |

tc生效点只能界定在命令开始/完成之间，不能精确认作进程返回时刻。下行缺口覆盖相对恢复生效的等待区间分别为731.87—735.78ms、746.74—757.26ms。同步统计明确占用恢复关键路径，但耗时不足以直接解释约0.74秒等待；即使以后移出关键路径，也可能改变重试相位，不能预先承诺固定收益。

两版ss均出现backoff=2、cwnd=1、RTO约832—848ms；命名空间TCPTimeouts均增加6、TCPLostRetransmit均增加4，RetransSegs分别增加8/6。结合接收端ACK缺口、后续覆盖和ACK前进，证据支持退避后的TCP恢复占主要等待。缺口覆盖后很快进入应用，首条解码/提交/预测合计约0.35/0.56ms，未出现可解释约60ms差额的固定解码成本。

候选首消息本轮晚14.53ms，但追到新鲜状态反而早28.92ms，新输入执行早21.08ms。原始参考收到首消息后继续追到新鲜状态用了61.44ms，候选为17.99ms。这个成对样本说明TCP相位与后续追赶会改变尾部形状，不能把上一轮约59—62ms差额归成稳定的压缩开销，也不能据此认定回归已消失。

### 抓包与归因边界

保留原loopback的MTU和offload，包头采集改用MSG_TRUNC取得实际SKB长度，以128字节缓冲读取头部，只保存序号等元数据。分别采集1210/1216条，丢包计数为0，时钟转换漂移均小于0.001ms。最大SKB为65549/15726字节，不能把这些聚合记录当作公网MSS报文数。零IP长度GSO路径经过合成数据验证，本轮实际记录未触发该路径。

原loopback使用egress qdisc，出站AF_PACKET观察点在发送路径的qdisc之后；被qdisc丢掉的原发及失败重试可能不可见。因此不能套用先前ingress的“重复序号即重传”分析。归因改用可观察的下行ACK缺口覆盖与ACK进展，再与ss/内核计数交叉核对；**不推断每次重试的精确发出时刻，不强行重建上行缺失字节或每个快照的TCP映射**。ACK自身也可能丢失或延迟，ACK时间不等于完整消息到达时间。这与[Linux发送路径源码](https://github.com/torvalds/linux/blob/v6.18/net/core/dev.c)中的qdisc与出站tap位置一致。

## 3. 30Hz健康页：延迟集中在原生收齐之后、JavaScript入口之前

浏览器窗口完成原S2-I1两次交火和恢复功能检查；新移动实际执行、权威位置变化、新射击、旧射击不补执行、执行配对确认、生命/房间保持及队列边界均通过。实际模拟离线905.04ms，恢复后新输入发送41.96ms、真正执行75.52ms、确认106.96ms，延迟到达作废26条输入。**健康页最大完整状态间隔160.80ms超过原150ms线，整个窗口失败。**

仅增加Default模式NetLog，不启用IncludeSocketBytes，不添加性能或后台调度开关。实际启动命令已保存；WebGL实际使用AMD RX9070XT/D3D11硬件后端。两个页面API均保持visible/focused，没有状态切换；长任务观察受支持且本段无记录。这些结果限制归因范围，不能排除全部浏览器内部调度。

健康端按间隔结束时刻分段，边界上的跨段间隔也计入，不能通过切窗漏掉最大间隔：

| 健康端最大值ms | 故障前900ms | 模拟离线期间 | 恢复后约824ms |
| --- | ---: | ---: | ---: |
| 服务器发布间隔 | 47.29 | 47.62 | 46.67 |
| 原生层收齐完整快照的间隔 | 47 | 48 | 47 |
| JavaScript入口间隔 | 51.70 | **161.00** | 50.30 |
| 完整状态应用间隔 | 51.60 | **160.80** | 50.20 |
| 单消息解码工作 | 0.20 | 0.50 | 0.20 |
| 单快照处理工作 | 0.30 | 0.30 | 0.20 |
| 单次渲染工作 | 6.20 | 5.50 | 5.20 |

最大间隔对应连续快照1070→1071：服务器发送间隔31.60ms、原生收齐间隔31ms、JS入口间隔161ms、完整应用间隔160.80ms。对应的原生收齐→JS入口等待从约195.60增至325.60ms，两条快照处理仅0.30/0.20ms。离线期间健康页该等待最大约498ms，同时渲染继续运行。**本轮超线主要发生在浏览器原生层之后、应用处理入口之前，证据不支持将其解释为服务器停发、TCP未交齐或应用解码/渲染长任务。**

NetLog的帧头事件并不保证帧体已经完整，[Chromium源码](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/websockets/websocket_basic_stream.cc)在组装完成前就记录帧头。本次按HTTP升级响应、全部帧头及载荷长度累计字节，再找原生socket读取覆盖帧尾的时刻；健康连接434940字节恰好等于129字节升级响应加434811字节帧流。291条JS消息的长度序列与原生流唯一连续匹配，受损连接也独立完成同样校验。没有把帧头时刻直接当作完整接收，分析只使用元数据，不保留消息载荷。

NetLog时间分辨率为1ms；绝对跨时钟等待还包含映射误差，相邻间隔不受常量偏移影响。本轮足以定位交付阶段，**不足以再区分CDP离线模拟的特有影响与Chrome一般消息调度行为，更不能认定真实双设备会出现同样问题**。CDP离线排队也不等同于内核丢包/RTO，其约76ms输入执行不能与Linux约811ms直接比较。完整配对和阶段数据见[browser-analysis.json](../artifacts/online-weak-network/20261115/three-diagnostics/browser-analysis.json)。

## 4. 失败保留、工程检查与建议

首次浏览器启动在任何页面/游戏创建前，读取Browser.getBrowserCommandLine被拒绝，因为实际启动没有enable-automation。失败报告与日志保留在browser目录；未添加该开关。随后通过SystemInfo取得本次拥有的浏览器PID，只读Windows CIM命令行，读取失败不会改变测试结果；在browser-ready目录完成唯一登记的浏览器业务窗口。没有追加通过性重跑。

TCP包头解析先用合成头部和本地AF_UNIX数据报核对大SKB、错误输入及MSG_TRUNC长度，未增加游戏/网络窗口。既有累计199项回归通过，工程检查96个格式/规则文件、99个运行模块通过；诊断选择边界与Python语法检查通过。运行源码、逻辑测试、依赖、构建与离线产物哈希保持；宿主TCP参数前后一致。审计见[source-audit.json](../artifacts/online-weak-network/20261115/three-diagnostics/source-audit.json)。这些工程通过不覆盖质量失败。

建议仍以低成本、可解释的工作为先，本轮未实施后续修复：

1. 后续可将qdisc统计移出故障恢复关键路径，保留故障前后证据，减少几毫秒夹具扰动；不能把它当作TCP退避的解决办法。
2. 浏览器后续若获授权做对照，优先验证CDP模拟/消息交付的隔离边界；现有证据不足以支持修改生产解码器、GPU开关或健康端150ms门槛。
3. TCP继续保持当前成熟架构和参数。本次没有证明简单可靠的生产修复，也没有提供重启发送窗口或替代传输的依据。O4及健康页质量问题保持未关闭，未进入S6。
